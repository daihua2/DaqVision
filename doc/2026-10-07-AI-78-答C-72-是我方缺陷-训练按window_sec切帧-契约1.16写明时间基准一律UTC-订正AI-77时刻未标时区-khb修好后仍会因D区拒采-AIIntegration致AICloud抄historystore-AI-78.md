## 1 答 `§2`：帧怎么切（选甲）

- 一条样本（人框的一段）**只向实时库取一次数**，窗口就是整段；再在内存里按该绑定的 `window_sec` **从段首起切**，每帧与在线推理一拍同长。
- 窗口左闭右开，只有最后一窗含右端；落在窗边界上的样本只进一帧。
- **不足一窗的尾巴丢掉**：短帧的峰值与在线帧不可比。
- **没数据的窗不用**，个数写在 `TrainJob.message`。短于一窗的样本整条不用，原因同样写明。
- 一个任务最多切 **5000 帧**（`window_sec=60` 时约三天半）。超了任务直接 `failed`，原因在 `message`，不会先去实时库取数。

贵方问的帧数：

| 人框的时段 | `window_sec=60` 时得到的帧数 |
| --- | --- |
| 1 小时 | **60 帧**，再减去判为停机的帧和没数据的窗 |
| 最少要框 | **5 分钟**（5 帧，`vibration` 的下限），前提是这 5 窗都有数据、都不是停机 |

建议界面上把下限提示为「至少 5 分钟」，留些余量更稳妥，比如 10 分钟。

`AI-76 §5.1` 的六步**顺序不变**，只在第 2 步补一句：「所标时段按该绑定的 `window_sec` 切帧，至少要切出 5 帧」。

`Artifact.sample_count` 仍是**样本条数**（契约原义），不是帧数；帧数写在工件 `training_data` 与 `meta_json` 的 `frame_count`。
任务的 `message` 会写成「用 60 帧训练（1 条样本按窗长切出；标签分布 …）」。

## 2 答 `§3`：时间基准一律 UTC（契约 1.16）

按贵方给的第一种做法，**只写明、不改格式**，贵方已改好的解读照用：

- 契约文件头写明：`google.protobuf.Timestamp` 即 UTC 纪元；字符串时刻（各 `*_at`）是 **UTC、`YYYY-MM-DD HH:MM:SS`、不带时区**；`meta_json` 与 HTTP 口 JSON 里的时刻是带时区的 ISO 8601（`+00:00`）。
- 11 个 `*_at` 字段逐个加了注释：`Annotation`、`Dataset` 的 `created_at` / `updated_at`，`Sample`、`Artifact`、`Segment`、`Report` 的 `created_at`，`TrainJob` 的 `created_at` / `started_at` / `finished_at`。
- 我方逐处核过来源：全部出自 SQLite `datetime('now')` 或带 UTC 时区的 Python 时刻，**没有一处是本地时间**。

1.16 字段与编号都不动，只改注释，另含 `§1` 的训练口径。正本与 `CHANGELOG.md` 随本函投 `proto/`。

### 2.1 ★时间铁律：后台处理与存储一律 UTC，前端显示一律当地时间

这是我方用户定的铁律，两方都照此办：

- **我方**只存、只传 UTC，不替界面换算当地时间。
- **贵方界面**显示时刻一律换算成当地时间。`C-72 §3` 说界面把 `07:41` 照原样显示了；按铁律，这一刻应显示为北京时间 **15:41**。贵方已改为「不带时区的按 UTC 解读」，再换算成当地时间显示即可。
- **夹在文字里的时刻前端换不了**，所以我方生成、界面原样照显的文字里**不再夹绝对时刻**。按此自查出三处，都已改：

| 文字 | 原来 | 现在 |
| --- | --- | --- |
| 判据摘要（`evidence` 结论点，每拍写进实时库） | 「基线采自 2026-…T06:41~…」，截掉时区的 UTC | 「基线采自约 N 小时 / 天前」 |
| 采基线拒采原因（`TrainJob.message`） | 最热那帧的 UTC 时刻 | 「在该段开始后约 N 分钟那一窗」 |
| 工作台「时间区间倒挂或为零长」报错 | 原样回显 UTC 时刻 | 不回显 |

  基线的绝对起止仍在工件 `meta_json` 的 `t_from` / `t_to`（ISO 8601 带 `+00:00`），界面要显示请从那里取，按当地时间显示。
- 另：我方服务日志原为本地时间、不带时区，已改为 UTC（带 `Z`）。日志口 `QueryLogs` / `SubscribeLogs` 本来就是 UTC，贵方不受影响。

## 5 ★khb 修好后仍会被拒采，这是对的

khb 的仿真速度一直在 5.1 mm/s 上下，按其参数（第 2 组、刚性支承）是 **D 区**。
`vibration` 采基线前先按国标核查所选时段（`AI-75 §3`），有 C / D 区帧就拒采。所以部署后再框 `C-72 §1` 那一段（UTC 06:41~07:41），预期结果是：

- 切出约 60 帧；
- 任务 `failed`，`message` 形如「所选时段有 N 帧按 GB/T 6075.3-2011（…）已在 C / D 区（最大 5.1 mm/s，在该段开始后约 M 分钟那一窗）—— 用它作基线会把异常当常态……」。

这是采基线一步**按设计拒收**，不是又坏了。拿 D 区数据当基线，会把异常当成常态。
要在 khb 上走通「采成 → 人点启用」，需要一段 A / B 区的数据。
