# AI 视觉识别研发计划（瑞芯微 RKNN → daqgate 集成）

> 配套方案：《有色矿山机械AR+AI视觉质检方案_优化版.pptx》
> 目标读者：AI 视觉零基础、但熟悉 daqgate（Go 网关）工程的你
> 编写日期：2026-06-03
> 本计划的定位：**把"从瑞芯微 GitHub 跑通官方 Demo"到"AI 视觉成为 daqgate 的一个数据源/能力"这条路，拆成可以一周一步推进的清单。**

---

## 0. 先读这一页：整体策略与心法

你现在的处境：
- 已有一套成熟的工业网关 `daqgate`（Go 后端 ProtocolGate + React Web + RN App），跑在瑞芯微平台（E52c / RK3582）上。
- 方案书已经把"卖什么、怎么分层"讲清楚了（AR + AI视觉 + NDT + 多模态）。
- 你个人对 **AI 视觉**这一块是零基础，想从**瑞芯微官方成熟库**起步，**渐进式**把视觉能力长进 daqgate。

那么这份计划遵循三条心法：

1. **先复现，再改造，最后集成。** 不要一上来就写自研算法。先把瑞芯微官方 Demo 在板子上跑出框，建立"模型→量化→板上推理"的完整肌肉记忆，再逐步替换成自己的数据和场景。
2. **算法是锦上添花，成像/工程化才是 90% 的工作量。** 方案书反复强调这点（成像 POC 优先）。本计划把大量篇幅放在"怎么把推理结果稳定地变成 daqgate 里的一条数据"，而不是调模型精度。
3. **视觉推理与 daqgate 解耦。** 视觉部分用独立的"推理服务（Sidecar）"承载，daqgate 把它当成**一个虚拟设备/数据源**接入，复用现有的 tagpoint→adapter→Web 链路。这样视觉模块崩了不影响网关采集，daqgate 也不用被 C/Python 的视觉依赖污染。

> 📎 **Go ⇄ Python 交互统一走 gRPC（不用 MQTT）**，具体接口契约见同目录《视觉算法gRPC交互方案_v1.md》。本文下面阶段 3/4 的"结果回传"均以 gRPC 为准。

> ⚠️ 一句话避坑：**RKNN 这条链最大的坑不是写代码，而是"驱动版本、运行库版本、Toolkit 版本三者必须严格匹配"**。第 0 阶段会专门处理它。

## 1. 目标对齐（从方案书提炼）

方案书把质量场景做了分层分工，**只有下面这几类真正归"AI 视觉"**，其余归 NDT / 3D测量 / AR / PdM：

| 检测对象 | 典型缺陷 | 手段 | 难度 | 是否本计划范围 |
|---|---|---|---|---|
| 车间安全（PPE/明火） | 没戴安全帽、没穿反光衣、明火烟雾 | 固定相机 + YOLO 检测 | ★低 | ✅ **一期首选练手** |
| 机加工件 | 漏孔、漏攻丝、刀痕划伤 | 工业相机 + YOLO 检测 | ★★中 | ✅ 二期 |
| 铸件/结构件表面 | 砂眼、披缝、磕碰、漏喷漆、色差 | 移动相机 + 无监督异常检测 | ★★★高 | ✅ 二期/三期 |
| 焊缝外观 | 咬边、焊偏、余高超差 | 工业相机 + 3D线激光 | ★★★高 | ⏳ 后期（需 3D，先不碰） |
| 物料追溯/铭牌 | OCR / 二维码 | 相机 OCR | ★★中 | ✅ 可选模块 |
| 内部缺陷 | 缩孔、未焊透、裂纹 | NDT（RT/UT/MT/PT） | — | ❌ 非视觉，不做 |

**本计划的技术主线（与方案书"自研 + RKNN"主线一致）：**

```
PyTorch/PaddlePaddle 训练  →  导出 ONNX  →  RKNN-Toolkit2 量化转换(INT8)  →  RKNPU2 板上推理  →  判定/告警  →  汇入 daqgate
```

**学习路径上的首个落地场景，强烈建议选「车间安全 AI（安全帽/明火检测）」**，理由：
- 开源数据集和预训练模型最多，瑞芯微 model_zoo 里直接有 YOLO 现成例子；
- 不依赖昂贵的工业相机/光源，普通网络摄像头 RTSP 流即可起步；
- 与方案书"一期·见效快"完全吻合，做出来能立刻演示。

> 表面缺陷（无监督异常检测）虽然是方案核心卖点，但它对成像和数据要求高，**不适合作为第一个练手项目**。放到第 5 阶段。

## 2. 关键技术决策（含推荐默认值）

下面三个决策会影响后面所有阶段。我给出**推荐默认值**，你可以先按默认值走，跑通后再调整。

### 决策 A：开发用什么板子？

| 选项 | 说明 | 建议 |
|---|---|---|
| **专门买一块 RK3588 开发板**（Radxa ROCK 5C / 香橙派 OrangePi 5 / firefly） | 完整 6 TOPS NPU、社区资料最全、与方案书部署目标一致 | ✅ **推荐**：约 ¥500–900，作为视觉研发主力机 |
| 直接用现有 E52c（RK3582） | RK3582 是 RK3588 的"缩配版"，NPU 算力/核数较弱，**部分批次 NPU 能力受限，需实测** | ⚠️ 可做网关协调，**不建议**当视觉训练/调试主力 |
| 先在 PC（x86）上用模拟器 | RKNN-Toolkit2 自带 simulator，可在 PC 上验证转换是否正确 | ✅ 转换/训练阶段必用，但**最终一定要上真板**测速度 |

> 推荐组合：**PC（训练+转换+模拟） + 一块 RK3588 开发板（板上推理验证） + E52c（最终作为数据网关）**。

### 决策 B：视觉推理怎么和 daqgate 配合？（最重要）

daqgate 是 Go 写的，NPU 推理生态是 C/C++/Python。强行用 CGo 把 `librknnrt.so` 绑进 Go 里，会把 OpenCV、视频解码等一大堆 C 依赖拖进 daqgate，得不偿失。**采用独立推理服务（Sidecar）+ gRPC 方案：**

```
┌─────────────────────────────────────────────────────────────┐
│  RK3588 边缘盒 / E52c                                          │
│                                                               │
│  ┌───────────────────────┐      ┌──────────────────────────┐ │
│  │  视觉推理服务 (Sidecar) │ 事件 │  daqgate / ProtocolGate   │ │
│  │  Python (gRPC SERVER)   │ 流   │  (Go, gRPC CLIENT)        │ │
│  │  - 取流(RTSP/USB)       ├─────►│  - channel/vision 新通道   │ │
│  │  - RKNPU2 推理(librknnrt)│ gRPC │  - 当作虚拟设备/tagpoint   │ │
│  │  - 判定/抓拍            │◄─────┤  - 复用 adapter→Web/上云   │ │
│  │  - 暴露 VisionInference │ 控制 │  - 缺陷图存档              │ │
│  └───────────────────────┘ unary└──────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

**回传通道：统一用 gRPC（不引入 MQTT）。** 角色：**Python 当 gRPC Server，daqgate 当 Client**（实现成 `channel/vision` 新通道，像 Modbus 通道连设备一样去连视觉服务）。详见《视觉算法gRPC交互方案_v1.md》。

| 方式 | 评价 |
|---|---|
| **gRPC**（Python Server / Go Client） | ✅ **本方案**：强类型、低延迟、与 daqgate 现有 `webservice`/`channel` 架构一致，控制+事件双向清晰 |
| ~~MQTT~~ | ❌ 不用：未来信息传输统一走 gRPC |
| CGo 直接绑定 librknnrt | ❌ 不用：依赖污染、goroutine 阻塞、难维护 |

> **推理服务用 C++ 还是 Python？** 练手/打通阶段用 **Python（rknn-toolkit-lite2 + grpcio）** 最快；性能调优/量产阶段换 **C++（rknn_model_zoo 的 C-API demo）**，吞吐和延迟更好。本计划 0–4 阶段用 Python，第 6 阶段再谈 C++ 化。

### 决策 C：第一个落地场景

**默认：车间安全 AI（安全帽 + 明火/烟雾检测），用 YOLO 检测模型。**（理由见第 1 节）

## 3. 瑞芯微开源库地图（你会反复用到的 GitHub 仓库）

这是"从瑞芯微 GitHub 成熟视觉识别库开始"的具体落点。**先收藏这几个仓库：**

| 仓库 | 作用 | 跑在哪 |
|---|---|---|
| **`airockchip/rknn-toolkit2`** | 核心工具链。PC 端：ONNX→RKNN 模型转换 + INT8 量化 + 模拟器；板端：`rknn-toolkit-lite2`（Python 推理） | PC + 板 |
| **`airockchip/rknn_model_zoo`** | **新手金矿**：YOLOv5/v8/v10/v11、PPOCR 等现成例子，含数据集、转换脚本、C++/Python 板上部署 demo | PC + 板 |
| **`airockchip/rknpu2`**（或 toolkit2 内置 runtime） | 板上 C-API 运行库 `librknnrt.so` + 头文件，C++ 推理用 | 板 |
| **`airockchip/ultralytics_yolo11`** | 瑞芯微魔改的 YOLO 训练/导出分支，导出的 ONNX 对 RKNN 量化更友好（避免常见精度回退） | PC |
| `ultralytics/ultralytics`（官方 YOLO） | 训练自己的检测模型用 | PC |
| `openvinotoolkit/anomalib` | 无监督异常检测（EfficientAD/PatchCore/PaDiM），导出 ONNX 后转 RKNN | PC（第 5 阶段） |

> 📌 **版本铁律**：`rknn-toolkit2` 版本 ⇆ 板上 `librknnrt.so` 版本 ⇆ 内核 `rknpu` 驱动版本，**三者大版本必须一致**（如都是 2.3.x）。版本错配是新手 90% 报错的根因。第 0 阶段会锁定版本。

### 阶段 0：环境与认知准备（打地基）

**目标**：建立 RKNN 工具链环境，锁定版本，理解整条链路的概念。

**步骤**：
1. 在 PC（Ubuntu 或 WSL2，Python 3.8–3.10）安装 `rknn-toolkit2`，记下版本号（如 2.3.0）。
2. 在开发板上确认 NPU 驱动：
   ```bash
   cat /sys/kernel/debug/rknpu/version    # 查 NPU 驱动版本
   # 或 dmesg | grep -i rknpu
   ```
   把板上 `librknnrt.so` 替换成与 PC Toolkit **同版本**的那个（rknn_model_zoo 里有对应 runtime）。
3. 在板上装 `rknn-toolkit-lite2`（板端 Python 推理库）。
4. 读完（不需要懂全部，建立概念即可）：
   - rknn_model_zoo 的 README + YOLO 例子的 README；
   - 理解 5 个词：**ONNX、量化(INT8)、校准集、NPU、推理(inference)**（见文末术语表）。

**交付物**：一份《环境版本登记表》（Toolkit 版本 / librknnrt 版本 / NPU 驱动版本 / 板型号），贴在本文件末尾或单独存档。

**验收**：`from rknn.api import RKNN` 在 PC 能 import 成功；板上能 `import rknnlite`。

**学习资源**：rknn-toolkit2 仓库 `doc/` 目录的快速上手 PDF。

**预计工时**：2–4 天（环境坑最多，别灰心）。

**风险**：版本错配 → 严格按"版本铁律"对齐。

---

### 阶段 1：跑通官方 YOLO Demo（建立全链路肌肉记忆）

**目标**：**不训练、不改代码**，把瑞芯微官方预训练 YOLO 模型在板子上跑出检测框。这是整条路的"Hello World"。

**步骤**：
1. 进 `rknn_model_zoo/examples/yolov8`（或 yolo11），下载它提供的预训练 ONNX。
2. 在 PC 上跑它的转换脚本：ONNX → RKNN（带 INT8 量化，用 demo 自带校准图）。
3. 先在 PC **模拟器**上推理一张测试图，确认能出框（验证转换没坏）。
4. 把 `.rknn` 模型拷到板上，跑板上 Python demo，对一张图推理，打印检测框坐标 + 画框保存。
5. 改成**对一段视频/RTSP 流**逐帧推理，看 FPS。

**交付物**：板上对图片/视频出检测框的截图 + 一个记录 FPS 的小笔记。

**验收**：板上能对任意图片输出"类别 + 坐标 + 置信度"，并知道**单帧推理耗时**（这决定后面能接几路相机）。

**预计工时**：3–5 天。

**风险**：板上 FPS 太低 → 先确认用的是 INT8 而非 FP16；确认模型输入分辨率（640×640 常见）。

---

### 阶段 2：用自己的数据训练 → 转 RKNN → 上板（核心技能闭环）

**目标**：以"安全帽检测"为例，走通**自定义数据**的完整闭环。这是你将来所有场景的通用流程。

**步骤**：
1. **找数据**：网上有公开的"安全帽检测数据集"（如 SHWD/Hard Hat Workers，VOC/COCO 格式）。先用公开集，不用自己标。
2. **训练**：在 PC 用 `airockchip/ultralytics_yolo11`（或官方 ultralytics）训练 YOLO 检测模型，得到 `best.pt`。
3. **导出 ONNX**：用瑞芯微魔改分支导出（关键：用它的导出方式，量化精度更稳）。
4. **转 RKNN + INT8 量化**：复用阶段 1 的转换脚本，**校准集换成你自己场景的几十张图**。
5. **上板验证**：板上推理，对比量化前后精度有没有明显掉点。

**交付物**：一个自己训练的 `.rknn` 安全帽检测模型 + 板上 demo 视频。

**验收**：板上能检测"戴/没戴安全帽"，召回率肉眼可接受。

**学习资源**：ultralytics 官方"训练自定义数据"教程 + rknn_model_zoo 的量化章节。

**预计工时**：1–2 周（含训练等待 + 调试）。

**风险**：
- 量化后精度大跌 → 增加/优化校准集、改用瑞芯微导出分支、必要时关键层用混合量化。
- 没有 GPU 训练慢 → 用云 GPU（AutoDL 等）租几小时。

---

### 阶段 3：把推理封装成"推理服务（Sidecar，gRPC Server）"

**目标**：把阶段 2 的脚本，改造成一个**长期运行的 gRPC 服务**：取流 → 推理 → 判定 → 通过 gRPC 事件流把结果推出去。这是与 daqgate 对接的前置件。接口契约见《视觉算法gRPC交互方案_v1.md》。

**步骤**：
1. 先落定 `vision.proto`（v1 草案已在交互方案里），Python 端 `grpc_tools.protoc` 生成桩代码。
2. 用 Python(grpcio) 写常驻 gRPC Server，实现 `VisionInference`：
   - 输入：RTSP/USB 摄像头流（先用一路）；
   - 处理：每 N 帧推理一次（控制节拍，别每帧都跑）；
   - 判定：命中产出 `VisionEvent`，如"未戴安全帽，score=0.87，bbox=[...]"；无命中定期发 `HEARTBEAT`；
   - 抓拍：命中时存带框图到本地，事件里带 `snapshot_id`，原图走 `GetSnapshot` 按需取。
   - `StreamEvents` 把事件 server-streaming 推出；`ApplyPipeline/StopPipeline` 接收控制。
3. 健壮性：摄像头断线重连（发 `PIPELINE_STATUS`）、推理异常不退出、日志。
4. 做成 systemd 服务，开机自启；传输用 Unix socket（同机）或 TCP+mTLS（分布式）。

**交付物**：一个常驻的 `vision-infer` gRPC 服务 + 用 grpcurl/脚本拉到的事件流样例。

**验收**：摄像头前有人不戴安全帽 → 几秒内 gRPC 事件流上出现一条 `DETECTION` 事件 + 本地有抓拍图。

**预计工时**：1 周。

**风险**：取流/解码占满 CPU → 用硬解（板子的 VPU/`mpp`），或降帧率/分辨率。

---

### 阶段 4：daqgate 集成（视觉成为网关的一个数据源）⭐

**目标**：让 daqgate **消费视觉事件**，把它当成一个"虚拟设备"，复用现有的 tagpoint → adapter → Web/上云 链路。这样视觉数据和你现有的 Modbus/SNMP 等协议数据**走同一套管理、展示、上报**。

**步骤（与 daqgate 现有结构对齐）**：
1. **接入层**：新增 `channel/vision` 通道（参照 `channel/modbus` 结构），作为 gRPC Client 连上阶段 3 的 Python 服务，`StreamEvents` 订阅事件流，带重连退避。**这是把视觉变成"一个协议通道"的关键。**
2. **建模**：在 `domain/` + `tagpoint/` 里把每路相机建成一个虚拟设备的几个测点（如：`helmet_violation`、`last_event_ts`、`last_snapshot_id`、`pipeline_online`、`fps`）。让视觉事件落进现有的数据模型，质量码复用现有 `StatusCode`。
3. **存储**：复用 `store/`（Pebble/SQLite）做命中事件落库；抓拍图存文件，测点里只存 `snapshot_id`/路径。
4. **上报/展示**：
   - 上云：复用现有 adapter，把视觉测点随其他数据一起上报平台；
   - Web：在 ProtocolWeb 加一个"视觉告警"视图（列表 + 缩略图），走现有 gRPC-web；缩略图经 daqgate `GetSnapshot` 拉取。
5. **联动（可选）**：命中告警时，通过 daqgate 已有的 IO/PLC 能力触发声光报警（对应方案书"PLC 联动"）。

**交付物**：在 daqgate Web 界面能看到视觉告警列表和抓拍图；视觉事件能随网关数据一起上云。

**验收**：从"摄像头前没戴安全帽"到"daqgate Web 上出现告警 + 云端收到"，端到端闭环跑通。

**预计工时**：1–2 周（看 daqgate 现有代码熟练度）。

**风险**：
- 不要把推理塞进 daqgate 进程内 → 始终保持 Sidecar 解耦。
- 测点模型设计先简单，跑通再扩展。
- 建议先用"空跑"骨架（Python 发假事件、Go 收流打日志）验证 gRPC 链路，再接真模型——**先通管道，再灌数据**。

> 这一阶段做完，你就完成了"把 AI 视觉识别加入 daqgate"的**最小可用版本（MVP）**。后面都是增强。

---

### 阶段 5：无监督异常检测（方案书核心卖点：少样本）

**目标**：上"只学良品、识别一切偏离"的无监督异常检测，解决"缺陷样本稀缺"——这是方案书相对竞品的差异化点（PatchCore/EfficientAD，100–200 张良品即可）。

**步骤**：
1. PC 上用 `anomalib` 训练 **EfficientAD** 或 **PatchCore**（先拿公开的 MVTec AD 数据集练手，再换自己工件的良品图）。
2. 导出 ONNX → RKNN 量化 → 上板（同阶段 2 流程，但异常检测模型转换更敏感，需重点验证）。
3. 接入阶段 3 的推理服务，新增"异常分数 + 异常热力图"输出。
4. 汇入 daqgate（同阶段 4）。

**交付物**：对某个工件表面的异常检测 demo（良品/缺陷区分 + 热力图）。

**验收**：用 100–200 张良品训练后，能标出明显的表面异常区域。

**预计工时**：2–3 周。

**风险**：
- 异常检测模型在 RKNN 上算子支持不全 → 优先选 model_zoo/社区已验证可转的网络（EfficientAD 相对友好）。
- 成像不行则一切免谈 → **务必先做成像 POC**（相机+镜头+光源），方案书第 13 页有选型口诀。

### 阶段 6：工程化与性能（量产前）

**目标**：从"能跑"到"能交付"。

**步骤/清单**：
1. **推理服务 C++ 化**：用 rknn_model_zoo 的 C-API demo 重写，跑满三核 NPU、多模型/多路并行，硬解码（MPP）流水线，消除积压延迟。
2. **gRPC 强化**：C++ 推理服务沿用同一 `vision.proto` 契约（与 Python 版接口一致，仅换实现），保证 daqgate 侧零改动平滑切换。
3. **模型管理**：模型版本化、可远程下发更新（对应方案书"模型迭代下发"），与 daqgate 的 OTA(`ota/`) 思路打通。
4. **指标/看板**：误报率、漏检率、单路延迟、NPU 占用，纳入 `metrics/`。
5. **多路/多工位**：按"路数 × 模型数 × 切片数 × 节拍"做 NPU 预算（方案书第 10 页），决定单板多模型还是多板/升级 Orin。

**交付物**：可量产部署的视觉边缘服务 + 验收指标看板。

**验收**：对照方案书第 21 页的合同验收指标（致命缺陷漏检 0、常规漏检 ≤0.5%、误判 ≤0.5%）做现场盲测。

**预计工时**：持续迭代，3–6 周起。

## 5. daqgate 集成架构详解（给工程化阶段的参考）

**原则：视觉推理与 daqgate 解耦，视觉结果作为"虚拟设备数据"汇入现有管线。**

```
摄像头(RTSP/USB)
   │
   ▼
[vision-infer 推理服务 (Python→C++), gRPC SERVER]
   │  取流→NPU推理(librknnrt)→判定→抓拍
   │  暴露 VisionInference: StreamEvents/ApplyPipeline/GetSnapshot
   │
   │  gRPC 事件流(server-stream) ▲ 控制(unary)
   ▼                            │
[daqgate / channel/vision (gRPC CLIENT)]
   │  连接/重连/心跳, 事件→测点
   │
   domain/ + tagpoint/  ← 建模为虚拟设备测点
   │
   ┌─────────┼──────────┐
   ▼         ▼          ▼
 store/   adapter→上云   webservice(gRPC-web)
(落库)   (随网关上报)      │
                          ▼
                  ProtocolWeb "视觉告警"视图
                  (缩略图经 GetSnapshot 拉取)
```

**复用 daqgate 既有能力，几乎不重造轮子：**

| daqgate 现有模块 | 视觉集成怎么用 |
|---|---|
| `channel/`（参照 modbus/snmp） | 新增 `channel/vision` 作 gRPC client 连 Python 服务 |
| `domain/` `tagpoint/` | 把视觉指标建成虚拟设备的测点 |
| `store/`（Pebble/SQLite） | 视觉事件落库 |
| `adapter`（上云发布） | 视觉测点随网关数据一起上平台 |
| `webservice/`（gRPC） + ProtocolWeb | 新增"视觉告警"前端视图 |
| `ota/` | 将来模型远程下发更新 |
| `hardware/` IO/PLC | 告警声光联动 |
| `metrics/` | 误报/漏检/延迟监控 |

## 6. 数据与模型管理（贯穿全程的好习惯）

- **目录约定**（建议在仓库外单独建数据区，别进 git）：
  ```
  vision-data/
    datasets/<场景>/{images,labels}/   # 原始数据+标注
    calib/<场景>/                       # RKNN 量化校准图(几十~200张现场图)
    models/<场景>/<版本>/{best.pt,model.onnx,model.rknn}
    snapshots/                          # 运行期告警抓拍
  ```
- **每个模型存一张"模型卡"**：训练数据来源、类别、输入尺寸、量化方式、PC精度 vs 板上精度、FPS。
- **校准集就用现场实拍图**——量化精度好坏，校准集代表性是关键。
- 标注工具：`LabelImg`（检测框）/ `X-AnyLabeling`（带模型辅助标注，更快）。

| 风险 | 影响 | 应对 |
|---|---|---|

## 9. 术语表（零基础速查）

- **ONNX**：一种通用的模型交换格式。各框架（PyTorch等）训练完先转成 ONNX，再转成各硬件专用格式。
- **量化 / INT8**：把模型权重从 32 位浮点压成 8 位整数，体积小、NPU 跑得快，代价是可能掉一点精度。
- **校准集（calibration set）**：量化时喂给工具的一小批代表性图片，用来统计数值范围，决定量化质量。
- **NPU**：神经网络专用加速器（瑞芯微 RK3588 有 6 TOPS）。CPU/GPU 也能跑 AI，但 NPU 最省电高效。
- **推理（inference）**：用训练好的模型对新图片做预测（出检测框/异常分数）。
- **YOLO**：最主流的实时目标检测模型系列，"给一张图，框出里面有哪些目标"。
- **无监督异常检测**：只用"良品"训练，凡是和良品不一样的都算异常。适合缺陷样本少的工业场景。
- **RKNN / RKNN-Toolkit2 / RKNPU2**：瑞芯微的 AI 部署全家桶——RKNN 是模型格式，Toolkit2 是 PC 端转换工具，RKNPU2 是板端运行库。
- **Sidecar（边车）**：和主程序（daqgate）并排跑的辅助独立进程，各管各的、通过消息通信。
