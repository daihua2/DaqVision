## 0 一句话

- **结构**：我方只用值里自带的 (`StructId`, `StructVersion`) 认，**不存结构名，也不存结构 id**。结构改名对我方取数、判级、已存绑定都没有影响；改按 GUID 识别，我方读路径也不需要 GUID。
- **字段**：我方按**字段名**认，绑定里存的就是字段名。字段原地改名，按字段的绑定会断（逐条落坏码并写明原因，不会静默）。改按字段号绑定约 1 个工作日，另需契约加一格。
- 实测出我方两处缺陷，都是我方解码缓存的问题，不需要别人配合，我方自改：
  1. 两个不同结构的描述**同名**时会静默错解（§3.1）；
  2. 原地修改（含现有的改单位、attrs）在我方**重启前看不到**（§3.2）。

## 2 影响与工作量（答 D-317 第 5 问、D-318 第 4 问）

### 2.1 结构改名

- 取数、判级、已存绑定都不受影响，这几处都不看结构名。
- `DescribeStructPoint` 回的结构名是现查的，**但走我方描述缓存**：改名后要到我方重启才显示新名（§3.2）。我方日志、坏码原因里写过的旧名不会改。AICloud 若存过结构名，请贵方自答。

### 2.2 结构改按 GUID 识别

- **读路径不需要 GUID**：我方只连一个实时库，库内 id 就够了。实时库给 `StructDef` 加 GUID 输出字段，我方刷新契约快照即可，旧快照不认也无害（proto3 未知字段）。
- **`DescribeStructPoint` 不加 GUID**：C-120 §2.2 说 GUID 对平台不是必需的；选 B 时平台请实时库在点表 `StoredPoint` 上给出，从点镜像取。平台日后要，加一格可加字段即可，加上测试与发函约半天。
- **方案 A**（点的 `StructRef` 改填实时库 id）：我方现在不建结构值点，不受影响；压装域将来重写时照新规矩填。附带一点：10-03 我方曾把 `StructRef` 填成 id，被实时库以「注册表里不存在」拒掉，后改填名。走 A 的话，实时库这一侧也要改。

### 2.3 字段原地改名（号不变、不发新版本）

- **按字段的绑定会断，但不静默**：绑定里存的是旧名，我方解码出来是新名，取数时那一路**逐条落坏质量码**，原因写明「v几 里没有字段 旧名」，该条诊断不出结论。要 AICloud 按新名重新提交绑定（重新提交照常核对）。
- **改名生效要等我方重启**：我方描述缓存按 (id, 版本) 为键，原地改名不变版本，所以重启前一直按旧名解（这期间绑定恰好照常工作），重启后才断，见 §3.2。断的时刻取决于我方何时重启，这比改名本身更麻烦。
- 解码本身不受影响：我方按字段号解码，号不变，旧值照样解得开。
- 订正 C-121 §2.1 一处：AI 绑定按旧名找不到字段时，我方**会报**，不是不报错。该路逐条落坏质量码并写明原因，结论点带坏码。只是 AICloud 那边看不到这层，要到结论点上才看得见。

### 2.4 改按字段号绑定

- **我方能做，约 1 个工作日**（含三环境测试，不含部署）：
  - 绑定提交时按名查到字段号，绑定表**另存字段号**（加列，老库迁移）；
  - 取数按号取；显示与核对报错用当前的名；
  - 字段号空的老绑定，第一次核对时补上。
- **契约**（接 C-121 §2.2「`role_fields` 改号要 AI 服务同意」）：
  - 改送字段号，我方不反对，具体形态等用户定了方案再定。
  - 我方倾向**另加一格**（例如 `role_field_numbers`，角色 → 字段号），`StructFieldInfo` 同时加 `number` 供平台选字段时取号。**不改现有 `role_fields` 的含义**：同一格里的字符串从字段名悄悄变成字段号，新旧两边对不上时不会报错。
  - 两格都是可加字段，升契约小版本。
  - 平台不改的话，`role_fields` 照旧收字段名，由我方换算成号存下，也能防住原地改名。
- **跨实时库**：我方的绑定本来就绑 globalId，是按库的，字段号跨库一不一致对我方没有影响，只关系平台的模板搬迁。

## 3 实测到的两处缺陷（我方自改，不需配合）

两处都用只读探针在两套测试环境（protobuf 4.21.12 / 7.36.1，后一套与现场同版）跑过，结果一致。

### 3.1 两个结构的描述同名时，静默错解

我方把各结构各版本的描述都放进**同一个**描述池，按消息全名取消息类型。两个不同的 (id, 版本) 描述同名时，第二个加不进池，我方会拿第一个的消息类型去解第二个的值：

```
结构 id 5「A」v1 字段 x(double)，值 x=1.25   → 解成 {'x': 1.25}
结构 id 9「A」v1 字段 y(float)， 值 y=2.5    → 解成 {'x': 0.0}   ← 应为 {'y': 2.5}，不报错
```

- **现行规则下不会发生**：库内结构名唯一，也不能改名。
- **允许改名后会发生**：例如 A 改名为 B，再新建一个结构叫 A。若新旧结构字段名相同、字段号不同，读出来的是看着正常的 0，绑定核对也拦不住。
- 改法：每个 (id, 版本) 用独立的描述池，不再靠全名区分。约十来行，加回归用例。

### 3.2 原地修改在我方重启前看不到

我方描述缓存按 (id, 版本) 为键、**永不过期**。原地修改不变版本，所以重启前一直用旧描述：

```
原地把字段 x 改名 x_vel、单位 mm/s 改 m/s（号不变、版本不变）
改前           → {'x': 1.5}      unit=mm/s
改后、同进程   → {'x': 1.5}      unit=mm/s   ← 看不到
改后、我方重启 → {'x_vel': 1.5}  unit=m/s
```

- **这一条今天就存在**，不等改名：D-302 已允许原地改单位、attrs，我方按字段绑定时核对的单位和物理量，在重启前用的仍是旧值。
- 改法：
  1. 绑定核对和 `DescribeStructPoint` 不走缓存，每次现取；
  2. 取数用的缓存加有效期，到期重取。实时库现行契约里的 `StructDef.modifiedMs` 可以用来判断变没变（我方契约快照要先刷新）。
  
  约半天，加回归用例。

**两处的时间安排**：§3.2 今天就存在，§3.1 改名上线前必须改好。我方打算两处一起改、随下一次部署上现场。部署照例经我方用户授权、先函告。
