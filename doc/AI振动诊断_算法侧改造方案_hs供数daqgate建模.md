> 目标架构：**hs(historystore) 负责数据 / daqgate 负责前端与实体管理 / Python 只负责 AI 诊断**
> 集成范式：沿用《AI视觉识别研发计划.md》+《视觉算法gRPC交互方案_v1.md》——
> **Python = gRPC Server（Sidecar），daqgate(Go) = gRPC Client（新增 `channel/diagnosis`）**

## 0. 两句话结论

1. **架构上**：v4 要从"web 单体"缩成一个**无状态推理 Sidecar**。删掉采集、删掉时序库读写、删掉台账
   JSON、删掉前端与报告；只留"特征 → 证据包 → 诊断结论"这条核心链，用 `diagnosis.proto` 暴露出去。
   代码量从 ~18.6k 行降到 **~3k 行量级**。

2. **算法上（更重要）**：算法能做到什么，完全由传感器决定。查完三家手册后的结论是
   **选型即算法**：
   - USR-G770 是 4G DTU 不是传感器；USR-SVT10 / LH-ST-485 **只出标量特征值**，
     用它们就只能做"烈度 + 趋势 + 异常预警"，FFT/包络/阶次/峭度全部失效。
   - **WT-VB02-485（v4 里原本就写着的那颗）不一样**：它直接输出
     **三轴 × (8 个阶次点 + 6 个阶次带) 的加速度谱能量 + 36 个时域指标 + 片上时间**，
     并且有 `RAWFIFO` 可按需取 1024 包原始波形。**这一颗就同时覆盖了轨 A 和轨 B。**
   - 因此本文保留双轨设计，但**首选硬件明确为 WT-VB02-485**，
     算法主线改为"吃传感器算好的阶次能量"，而不是自己做 FFT。

## 1. 硬件事实核查（决定算法上限）

### 1.1 USR-G770 是什么

依据官方《USR-G770 说明书 V1.0.6》（www.usr.cn/Down/USR-G770_V1.0.6.pdf）：

| 项 | 事实 |
|---|---|
| 定位 | **4G LTE DTU**，"RS232/RS485 To LTE"，2019-04 发布 |
| 能力 | 2 路 Socket **透传**、单路 UDC 模式、注册包/心跳包、类 RFC2217、AT 指令配置、9–36V 供电 |
| 不具备 | ❌ 不是传感器、无振动测量、**无 Modbus 主动轮询**、无边缘 JSON/MQTT 点位上报 |

**它只是一根"无线串口延长线"。** 所以现场链路必然是：

```
振动传感器(RS485 / Modbus RTU) ──串口──► USR-G770 ──4G透传──► 服务端 Socket
                                                              │
                                                    daqgate channel/modbus
                                                    (RTU over TCP，做主站轮询)
```

即 **daqgate 侧不需要新协议**，用现有 Modbus 通道 + "RTU over TCP / 透传 Server" 即可，
G770 对 daqgate 是透明的。这条不需要 Python 参与。

> ⚠️ 说明：你给的 wiki 链接 `usr.cn/wiki/puba/Z0G3TOJZP` 是 JS 动态渲染页，抓取为空白，
> 以上依据官方 PDF 说明书与产品页。**若现场用的是别的型号（尤其是能传原始波形的），
> 请把型号或那页内容给我，本文 §1.5 的可行域判定要跟着改。**

### 1.2 传感器给什么数据（关键 —— 已按官方寄存器表逐条核实）

> 核实方式：2026-08-12 用浏览器打开有人知识库（`usr.cn/wiki`，JS 渲染页，需浏览器不能靠抓取），
> 逐份读取产品手册原文与寄存器表。**有人产品线里振动传感器一共只有两款**，两款全部核实完毕。

**① USR-SVT10-01B（加速度型，测项最全的一款）—— 完整寄存器表 4.3 节：**

| 功能码 | 寄存器 | 内容 | 单位 | 类型 |
|---|---|---|---|---|
| 03H | 0000H | 温度值 −400~1500 | 0.1℃ | short |
| 03H | 0001H/0002H/0003H | **X / Y / Z 轴振动速度** 0~200 | 0.1 mm/s | unshort |
| 03H | 0004H | 固件版本号 | | unshort |
| 03/06H | 0006H | 设备地址 1~240（读写） | | unshort |
| 03/06H | 0007H | 波特率 1~10（读写） | | short |
| 03H | 0009H / 000AH / 000BH | **Z 轴** 加速度 0~1500 / 位移 0~5000 / 频率 10~1600 | 0.01g / μm / Hz | unshort |
| 03H | 000EH / 000FH / 0010H | **Y 轴** 加速度 / 位移 / 频率 | 同上 | unshort |
| 03H | 0013H / 0014H / 0015H | **X 轴** 加速度 / 位移 / 频率 | 同上 | unshort |

**寄存器地址到 0015H 为止，全表 16 个有效数据点，全部是标量。没有任何频谱、谱线、
波形、FFT 相关寄存器。** 检测周期与发送条件均为 500 ms；RS485 + Modbus RTU；
出厂 9600 8N1、地址 01、广播地址 250(FA)；DC 9–28V；IP65；M8×10mm 螺纹或磁吸。
（SVT10-01A 更简，只有温度 + 三轴速度。）

**② LH-ST-485 振动传感器（郎汉德 LonHand OEM，挂在有人"智慧感知设备"下）：**

| 功能码 | 寄存器 | 内容 | 说明 |
|---|---|---|---|
| 03H | 0x0000 | 温度值 | short, ×0.1℃ |
| 03H | 0x0001/0002/0003 | X / Y / Z 轴数据（速度） | short, ×0.1 mm/s |
| 03H | 0x0004, 0x0005 | 空 | short |
| 03/06H | 0x0006 / 0x0007 / 0x0008 | 主机编号 / 串口波特率 / 温度变化值 | 读写 |

**全表 9 个寄存器，比 SVT10 更简陋**（只有速度，无加速度/位移/频率），同样**无频谱**。
量程 0–50 mm/s、频率范围 10~1600 Hz、精度 ±1.5%F.S.、DC 12–24V、IP67、数据"实时，被动应答"。
另有 LH-ST-LoRa 版本（同系列，通信方式不同，测项不会更多）。

**结论：有人（含其代理的郎汉德）在售振动传感器，无一具备频谱输出能力。**

### 1.3 ★ WT-VB02-485（维特智能）—— 这一款满足要求，且它就是 v4 里写着的那颗

> v4 `sensors.json` 的 `sensor_model` 字段原本就写着 `MEMS / WT-VB02-485 / PCB 352C33`。
> 2026-08-12 按官方语雀手册《VB02新版说明书-1021x》逐条核实。

**基本参数**：三轴，量程 速度 0~600 mm/s、位移 0~60000 μm、频率 5~2000 Hz；精度 <F.S±4%；
IP68；耐冲击 20000g；9~36V / 10mA@12V；RS485 Modbus RTU，波特率最高 **230400**；
从站默认地址 0x50；磁吸或 M8 螺纹安装。

**它给的不只是特征值，而是一整套"传感器算好的结构化频谱"**（Modbus 0x03 可读）：

| 地址段 | 内容 | 数量 |
|---|---|---|
| 0x30~0x33 | **片上时间**（年月日时分秒毫秒，可读写） | 4 |
| 0x34~0x36 / 0x3A~0x3C / 0x41~0x43 / 0x44~0x46 | 三轴 加速度 / 速度 / 位移 / 频率 | 12 |
| 0x40 | 温度（**芯片温度，非外部接触温度**） | 1 |
| 0x47~0x6A | 三轴 × 12 个时域指标：波峰因素、峭度、绝对平均、方差、**RMS**、波形指标、峰值指标、脉冲系数、偏斜度、速度RMS、速度峭度、位移RMS | 36 |
| 0x6B~0x6D | 三轴 **故障诊断** ERRX/Y/Z（⚠️ 手册未给位定义，需问厂家） | 3 |
| **0x6E~0x9A** | 三轴 × （**8 个阶次关注点** + **6 个阶次关注带** + 总能量） | **45** |

**阶次能量的定义（关键）：**

- 关注点 POINT1~8 = **1/4X、1/2X、1X、2X、3X、4X、5X、6X** 的加速度谱能量
- 关注带 AREA1~6 = **0~1/2X、1/2~1X、1~2X、2~3X、3~4X、4~5X** 的频段能量
- 基频由寄存器 `0x2A BASEBAND` 配置（"关注 30Hz 就把基频设为 30"）

**可配置项**：`0x29 SR` 采样率 ~~9 档~~ **10 档**（2026-09-19 订正：手册列 `0x00~0x09` 共 10 档）（64Hz ~ **32KHz**，对应可测频率 0.1~32Hz ~ 128~16KHz）；
`0x07 MODE` 算法模式（时域低频 10~200Hz / 时域高频 / **频域**）；`0x2B DRM` 位移量程模式；
写寄存器需三步（解锁 `0x69` → 写 → 保存 `0x00`）。

**★ `0x2C RAWFIFO` 原始加速度 FIFO：一次读回缓存的 1024 包原始加速度数据。**
即这颗传感器**既能出结构化频谱，也能按需出原始波形**。

**带宽账**：0x34~0x9A 共 103 个连续寄存器 = 206 字节，Modbus 0x03 单次上限 125 寄存器，
**一次请求就能把全套结构化频谱读完**。1 秒一次 = 206 B/s，10 秒一次 = 20 B/s，
对比 v4 现在的 3000 点/秒，**降了三个数量级**。

**⚠️ 选型必须实测验证的三点：**

1. **精度 <F.S±4%**。若速度量程固定 600 mm/s，则误差可达 ±24 mm/s ——
   而 ISO 10816 的 A/B/C 区判据线在 2.8 / 7.1 / 18 mm/s 附近，**误差会把整个判据淹没**。
   手册自己的举例是按当前量程算的（3000μm 时误差 120μm）。**上台架标定前不要承诺 ISO 分级精度。**
2. **能量寄存器无量纲**。手册只写 `=((H<<8)|L)`，没给单位和缩放系数，**必须实测标定**。
3. **温度是芯片温度不是接触温度**（SVT10 是接触温度）。**不能当轴承温度用**，
   温升类判据要么放弃，要么另配温度测点。另注意频率下限 5Hz，低频场景不适用。

#### 1.4.1 从横评读出来的四条

1. **谱能力不是某家私有设计**。维特（关注点/关注带）、仁科（频点/频带）、朗尚（频点/频带）
   三家**互不相干却收敛到同一套概念**：`频点能量 + 频带能量 + 转频倍数可配 + 谱总能量`。
   ⇒ 按它建语义字典风险很低，后来的厂家大概率能套进来。
2. **统计口径是最隐蔽的坑**。仁科明写"速度=均方根值、位移=峰峰值、加速度=均方根值"，
   其余三家**只写"振动速度"不注明口径**。RMS / 峰值 / 峰峰值之间差 √2~2√2 倍，
   **混用不会报错，只会让 ISO 判级整体偏移一档**。⇒ 口径未明的型号必须标定后才能进 L1+。
3. **精度标注差一个数量级，且口径不同不能直接比大小**：
   满量程 4%（维特 ±4 mm/s、朗尚 ±8 mm/s）vs 读数 1%（仁科约 ±0.1 mm/s）。
   ISO 10816-3 Group 2 刚性的判据线是 **1.4 / 2.8 / 4.5 mm/s** ——
   **±4 mm/s 横跨 A/B/C 三档**。⇒ 按满量程 4% 标注的型号，**理论上撑不起 ISO 绝对分级**。
   但实际误差通常远好于标称，**正解是台架标定，不是照标称值取舍**。
4. **没有一款给完整谱线**。五款（含朗尚共六款）**无一家**输出 400/800 线谱数组；
   谱一律以"频点/频带能量的定长标量组"出现。唯一的变长数据是维特 `RAWFIFO`。
   ⇒ 可收敛为一句：**全谱不走 Modbus**。这直接支撑了 §2.3 "hs 这一期不需要结构化存储"的结论。
   ★（2026-09-19 订正）"全谱不走 Modbus"仍成立，但 §2.3 那条结论**已被取代**，见 §2.3 开头的订正说明。

#### 1.4.2 ⚠️ 本节不是选型结论

用户已定（daqgate r3）：**选型不定，几种型号只是设计参考，目标是"能兼容各类型传感器"。**

⇒ **本表的作用是证明"能力差异真实存在且是结构性的"**，从而支撑
§1.5 的能力分级与 daqgate 的能力声明机制；
**不是"哪家更好"的论据**。算法侧不绑任何厂牌，按测点的实际能力集判档。

### 1.5 算法能力分级 —— 五档 × 六型号矩阵

> **本节取代原先"按型号写可行域"的写法。** 用户已定：**选型不定，目标是兼容各类型传感器**
> （daqgate r3）。因此算法**按能力分档组织，不绑厂牌**；型号只作为"能力差异真实存在"的样本证据。
> 与 daqgate 的约定见协调文 r4。

#### 1.5.1 五档定义与最小能力集

字典名沿用 daqgate 语义字典 v0（`{设备}_{轴}_{量}_{口径}`，下表省略设备段）。

| 档 | 能力 | **最小能力集** | 台账前提 |
|---|---|---|---|
| **L0** | 不可诊断 | — | — |
| **L1** | 烈度 + 趋势 | `{axis}_v_rms` × ≥1 轴 | — |
| **L1+** | ISO 绝对分级 | L1 且**口径确为 RMS** 且**精度撑得住判据** | `iso_group` + `mount_type` |
| **L2** | 故障类型判别（不平衡/不对中/松动） | L1 + `{axis}_e_p1..p8` + **可信转速** | `rated_speed_rpm` 或转速源 |
| **L3a** | 轴承冲击检出 | L2 + `_kurt` / `_crest` / `_impulse` 任一 | — |
| **L3b** | 轴承**零件级**定位 | L2 + `brg_inner/outer/ball/cage` 四项齐全 | `bearing_model`（校验用） |
| **L4** | 波形重算（自定义包络解调等） | `raw_accel_frame` + 采样率元数据 | — |

#### 1.5.2 ★ 型号 × 能力档 矩阵

依据六份**官方寄存器表原文**（存档见 [`doc/传感器资料/`](传感器资料/) 与 daqgate 语义字典 v0）。
✅=满足 ❌=不满足 ⚠️=有条件满足。

| 型号 | 量的规模 | **L1** | **L1+** | **L2** | **L3a** | **L3b** | **L4** | 卡在哪一步 |
|---|---|:--:|:--:|:--:|:--:|:--:|:--:|---|
| 郎汉德 **LH-ST-485** | 4 项 | ✅ | ⚠️ | ❌ | ❌ | ❌ | ❌ | 无谱能量 ⇒ 止步 L1 |
| 有人 **SVT10-01A** | 4 项 | ✅ | ⚠️ | ❌ | ❌ | ❌ | ❌ | 同上（与郎汉德同源贴牌） |
| 有人 **SVT10-01B** | 13 项 | ✅ | ⚠️ | ❌ | ❌ | ❌ | ❌ | 同上。多的 9 项是位移/频率/加速度，仍无谱 |
| 仁科 **WZ3/WZ1**（基础型） | 13 项 + 校准系数 | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ | 同上，但**口径明写 + 精度高**⇒ L1+ 无条件成立 |
| 朗尚 **LVIB100** | 未知 | ✅ | ❌ | ⚠️ | ⚠️ | ❌ | ❌ | **协议手册不公开、点表建不出来**；且 FS±4% @0~200mm/s ⇒ ±8 mm/s，**L1+ 直接出局** |
| 维特 **WT-VB02-485** | 103 项 + RAWFIFO | ✅ | ⚠️ | ✅ | ✅ | ❌ | ✅ | **无轴承特征值** ⇒ 止步 L3a；`RAWFIFO` 使其成为唯一能到 L4 的型号 |
| 仁科 **RS-WZ3P**（频谱型） | ~120 项 | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ | **唯一能到 L3b**；无原始波形 ⇒ 到不了 L4 |

**⚠️ 三处"有条件"的具体条件：**

| 标记 | 条件 |
|---|---|
| 郎汉德 / 有人SVT10 / 维特 的 **L1+** | 手册**未注明统计口径**（速度是 RMS 还是峰值？），必须台架标定后才能进 L1+；且维特 `<F.S±4%` @0~100mm/s ⇒ ±4 mm/s，**横跨 ISO 的 A/B/C 三档**，标定结果大概率不达标 ⇒ 实际停在 L1 |
| 朗尚 的 **L2 / L3a** | 规格表写"提供频点、频带谱能量""峭度值"，**理论上够 L2/L3a**，但**协议手册不公开、寄存器地址未知 ⇒ 点表建不出来**。要用必须先向厂家索要协议手册 |

#### 1.5.3 三条从矩阵读出来的结论

1. **L2 是一道硬门槛，六款里只有三款过得去**（维特、仁科 WZ3P、朗尚——后者还卡在文档）。
   **没有频点/频带谱能量的型号，永远只能做"振动升高了"，不能说"是不平衡"。**
2. **L3b 目前只有仁科 WZ3P 一款**。轴承四特征值是包络解调的产物，
   其余五款要么没有、要么得靠 L4 自己算（仅维特可行）。
   ⇒ 若客户要"换哪个件"级别的结论，**选型上这一条几乎是单选题**。
3. **L1+ 与 L2 的门槛互相独立**：仁科基础型能做 ISO 绝对分级却判不了故障类型；
   维特能判故障类型却做不了可靠的 ISO 分级。**两者不可互相替代**，
   要同时要就得选仁科 WZ3P，或者接受混配。

#### 1.5.4 部署形态：混配是常态，不是例外

daqgate r3 §1.1 算出经 MQTT 网关中转时的挂载上限：

| 型号形态 | 点/台 | 单网关可靠台数（≤3 包） |
|---|---|---|
| **郎汉德 LH-ST-485 / 有人 SVT10-01A**（4 项） | 4 | **61** |
| **有人 SVT10-01B / 仁科 WZ3·WZ1**（13 项） | 13 | **18** |
| **维特 VB02 全量 / 仁科 WZ3P**（103 / ~120 项） | 103 / ~120 | **2** |

⇒ **上谱能量型号后单网关只能挂 2 台。** 这决定了现场必然是混配：
**关键机组配 L2/L3 型号（每网关 2 台），一般点位配 L1 型号（每网关 18 台）。**

⇒ 因此本方案的算法**按测点独立判档**，同一台机组的驱动端与非驱动端可以处在不同档位。
**不需要、也不应该追求全厂统一型号。**

#### 1.5.5 与 v4 现有算法的对应

| v4 现有算法 | 归属档位 | 说明 |
|---|---|---|
| FFT 全频谱 / 瀑布图 | **无档可归** | 六款**无一家**给谱线数组，全谱不走 Modbus。此能力作废 |
| 阶次幅值 1X~5X | L2 | 由 `_e_p1..p8` 直接替代，且多了 1/4X、1/2X 分数阶次 |
| 峭度 / 波峰因素 / 波形因子 | L3a | 传感器算好，`signal_processing.py` 的时域部分不再需要跑 |
| 包络解调谱 | L3b（仁科直接给）或 L4（维特自算） | v4 原实现只在 L4 路径下才用得上 |
| 频谱图喂多模态 LLM | 作废 | 无谱线即无图。改为**用频点/频带能量构造文本证据** |
| ISO 烈度 | L1+ | 保留，但要过精度与口径两关 |
| 趋势 / 基线 / 异常检测 | L1 | 保留，是覆盖面最广的一档 |
| 规则 / kNN / MLP / LLM 汇总 | L2 起 | 证据包结构保留，**特征向量按档位动态组装** |

## 2. "只传频谱不传波形"这条路 —— 传输约束与 hs 存储形态

> 这一节记录该技术路线的**推导过程与结论修正**，是 §1 选型和 §3 算法设计之间的桥。

### 2.1 前提：原始高频波形不可能传

现场经 4G（G770 这类 DTU 或网关自带 4G）回传，原始波形的量级根本不成立：

| 方案 | 数据量 | 可行性 |
|---|---|---|
| 原始波形连传（25.6 kHz × 3 轴 × 4 B） | **307 KB/s** | ❌ 4G 不可能，且没有意义 |
| v4 现状（1 kHz × 3 轴，逐点写库） | 3000 点/秒 | ❌ 已被 12h 保留策略"自我了断" |
| 一帧完整频谱（800 谱线 × 3 轴 × 4 B） | 9.4 KB/帧 | ✅ 10 分钟一帧 ≈ **16 B/s** |
| **VB02 的一组结构化频谱**（103 寄存器） | **206 B/次** | ✅ 1 秒一次 ≈ 206 B/s；10 秒一次 ≈ 20 B/s |

**所以"传感器侧算好、只回传结构化结果"是唯一成立的路线**，不是妥协。
补充一个反直觉的点：即便走 Modbus RTU，整帧频谱也传得动 ——
9.4 KB = 4800 个保持寄存器，单次 0x03 上限 125 个 → 约 39 次读，115200 bps 下整帧 ~1 秒。
**只要不是连续传，而是周期式/触发式传，链路完全够用。**

### 2.2 由此推出的原始判断：hs 要支持结构化数据

频谱不是标量。一帧频谱是**一条结构化记录**：

```
{ 起始时刻, 采样率, 谱线数, 频率分辨率, 窗函数, 量纲(峰值/有效值),
  转速, 轴, amp[0..N-1] }
```

用 N 个独立测点去装 N 条谱线是灾难：测点数爆炸、时间戳语义错乱、
查询无法整帧取回、也无法表达"这一帧的窗函数是 Hanning"这类帧级元数据。
**据此判断：hs 需要在标量 VQT 之外，长出"结构化 / 数组型记录"这一类存储。**

### 2.3 结论修正：按 VB02 的实际形态，这个需求要分两层

> ★**2026-09-19 订正：本节对「阶次点/带能量」的结论已被取代**（原文保留，不改）。
> 用户裁定：维特 `0x6E~0x9A` 这 45 个阶次能量**做结构值、每轴一条记录**，不是 45 个普通测点。
> 本节的理由（定长、每项有独立名字、hs 不用改）只回答了"能不能拆"与代价，
> **没问算法是否依赖"出自同一张谱"**——而 1X 占比、2X/1X 这类判据恰恰依赖；
> 拆成标量后，任一个点的死区/SDT 就会让同一时刻的比值混了两张谱且不报错。
> 代价那条的前提（hs 无结构存储）也已由 `H-260` 改变。
> 时域指标 36 个与基础量**仍为普通测点**，不受影响（但基础量里的 `AX/AY/AZ` 与 `RAWFIFO` 是同一个结构，
> 不算标量，见 [整理版](传感器资料/WT-VB02-485_寄存器地址表_整理.md) §9.3）。
> 详见 [结构VQT与波形数组定义.md](../AIIntegration/doc/结构VQT与波形数组定义.md) §6.1 判据乙、§6.2。

选定 WT-VB02-485 之后，上面的判断**一半成立、一半可以延后**：

| 数据 | 形态 | hs 要不要改 |
|---|---|---|
| 阶次点/带能量 + 时域指标 + 基础量（0x34~0x9A，103 项） | **定长的一组标量**，每项都是独立物理量、各有单位 | ❌ **不需要**。用 103 个普通测点承载即可，daqgate 现有建模能力就能做，完整 VQT 天然成立 |
| `RAWFIFO` 的 1024 包原始加速度 | **变长数组 + 帧级元数据**（采样率、量程模式、起始时刻） | ✅ **需要**，这才是真正要 hs 长结构化/数据块能力的地方 |

**核心区别在于"定长小结构"和"变长数组"**：
VB02 给的不是 800 条谱线，而是 8 个阶次点 + 6 个阶次带 —— 每一项都是有物理含义、
有独立名字的量（"1X 加速度谱能量"），本来就该是一个测点，不是数组的一个下标。

**结论：hs 的结构化存储需求，从"必须、卡在关键路径上"降级为"轨 B 才需要"，可以往后排。**
第一阶段（吃阶次能量做诊断）**hs 一行代码都不用改**。

### 2.4 测点规模与采集节拍

103 点/传感器 × 20 传感器/网关 ≈ 2060 点。若全部 2 Hz 更新 ≈ 4 kpts/s。
建议**分频采集**，把速率压下来：

| 组 | 内容 | 建议节拍 |
|---|---|---|
| 基础量 | 三轴 速度/加速度/位移/频率 + 温度（13 点） | 1 s |
| 阶次能量 | 8 点 + 6 带 + 总能量 × 三轴（45 点） | 10 s |
| 时域指标 | 12 项 × 三轴（36 点） | 10 s |
| 原始波形 `RAWFIFO` | 1024 包 | **仅异常触发时**拉一次 |

按此节拍：13 pts/s + 81/10 pts/s ≈ **21 点/秒/传感器**，一个网关 20 个传感器约 420 点/秒 ——
对比 v4 现在**单个传感器**就 3000 点/秒，**降两个数量级**，正是 hs 的舒适区。

### 2.5 遗留待办

- **hs 结构化记录契约**（服务于 RAWFIFO 波形帧）：记录结构、查询语义、与 VQT 的关系、
  存储估算 —— 不在第一阶段关键路径上，但轨 B 启动前必须定。
- 若日后换成能出**完整谱线**的传感器（如 VB05/VB05D 或他厂 800 线机型），
  §2.2 的原始判断重新成立，hs 结构化存储回到关键路径。**这条要留着，别把结论写死。**

## 3. 算法双轨设计

### 轨 A：特征值链路（G770 + SVT10 类传感器，**现在就能落地**）

输入：每 500ms 一组
`vel_x/y/z (mm/s)`、`acc_x/y/z (g)`、`disp_x/y/z (μm)`、`freq (Hz)`、`temp (℃)`

四层算法，由浅入深，**每层都能独立出结论**：

**① 烈度判级（ISO 10816-3 / ISO 20816）— 立即可用、有国标背书**

用速度 RMS（10–1000Hz 带内）按机组类别与安装方式分 A/B/C/D 四区：

```
A 区 新交付机器      B 区 可长期运行      C 区 不宜长期运行(需安排检修)     D 区 有损坏危险
```

- 需要的配置：机组功率等级 / 刚性或柔性支承 → 决定 A/B/C/D 的边界值
- 产出测点：`iso_zone`(枚举)、`iso_margin`(离下一档还有多远)
- **这是最该先做的**，因为它把"数值"变成"该不该停机"，是客户唯一真正关心的输出

**② 基线与趋势（无监督，对齐视觉方案的"只学良品"思路）**

- 开机后采一段**已知正常运行**的数据当基线（对应视觉的"良品集"），
  存每个测点的 μ/σ、分位数、以及三轴之间的比例关系
- 在线指标：
  - `z_score` = (当前 − μ)/σ，逐通道
  - `ewma_trend`：指数加权均值的斜率（劣化速度，dB/天）
  - `ratio_drift`：三轴比例漂移（不平衡→径向增大、不对中→轴向增大，**这是没有频谱时判故障类型的主要抓手**）
  - `temp_rise`：温升相对基线（轴承劣化的独立佐证）
- 产出：`anomaly_score`、`is_anomaly`、`days_to_threshold`（按趋势外推的剩余可用天数）

**③ 多变量异常检测（轻量，不需要 torch）**

维度只有 10 上下、样本 2 Hz，用 `IsolationForest` 或 `EllipticEnvelope`（scikit-learn）足够；
再重也就 `PCA + T²/SPE` 统计量。**明确不要在这层用深度模型**——数据维度不支持，
而且 v4 那 2.1 GB venv（torch 占大头）在边缘盒上是纯负担。

**④ 故障类型倾向 + LLM 解释（复用 v4 最好的那部分设计）**

v4 的 **证据包（evidence package）** 设计可以原样搬过来，只换证据内容：

```
证据包 = { 测点元数据(设备/转速/功率/支承类型)
          + 当前特征值(V/A/D 三轴 + 温度 + 频率)
          + ISO 分区结论
          + 基线偏离(z-score / 三轴比例漂移 / 温升)
          + 趋势(斜率、外推)
          + 规则引擎结论
          + kNN 近邻历史案例 top5
          + 专家知识卡 }
   → prompt（闭集标签 + 强制 JSON + 全中文）→ LLM → 结论 + 建议检查项
```

规则引擎的判据要重写（没有阶次了），改成经验判据，例如：

| 现象 | 倾向 |
|---|---|
| 径向(X/Y)速度 RMS 显著大于轴向(Z)，且随转速平方增长 | 不平衡 |
| 轴向(Z)占比异常升高 | 不对中 / 联轴器问题 |
| 高频加速度 RMS 抬升但速度 RMS 变化不大，伴温升 | 轴承早期劣化 |
| 三轴同时抬升、宽带、无方向性 | 松动 / 基础问题 |
| 仅温度升、振动无变化 | 润滑 / 冷却问题，非振动源 |

> 这些判据的置信度**明显低于频谱诊断**，所以输出必须带"证据不足"的诚实表达——
> 让 LLM 在 `conflict` 字段里说清"无频谱数据，本结论为倾向性判断，建议现场加装波形采集复核"。
> **不许把低置信结论包装成确诊**，这条要写进 prompt 的 system 段。

### 轨 B：波形链路（要真频谱诊断时才启用）

触发条件：客户要"轴承内圈/外圈/滚动体"这种**精确到零件**的诊断。
那就必须换硬件（IEPE 加速度计 + 采集卡，或支持原始波形上传的智能传感器），
此时 v4 现有的 `signal_processing.py`（FFT / 包络 / 阶次 / 能量分布）**原封不动可以复用**，
它是 v4 里质量最好的一个文件。

波形怎么进系统，是本方案唯一悬而未决的架构问题：

| 方案 | 说明 | 评价 |
|---|---|---|
| B1 波形不进 hs | daqgate 把波形帧直接转给 Python 推理（gRPC 请求体里带），Python 算完只回结论 | ✅ **推荐**：hs 保持纯标量时序库不变形；波形是"过路数据"不落库 |
| B2 波形进 hs 做 blob | hs 长一个数据块能力 | ⚠️ 改动大，需 hs 侧专门设计，另议 |
| B3 波形单独存对象存储 | 另起一套 | ⚠️ 多一个运维件 |

**建议先按 B1 设计接口**（`DiagnoseWaveform` 请求里直接带 float 数组），
这样即便将来改成 B2/B3，Python 侧接口不用动。

### 4.3 接口契约草案 `diagnosis.proto`

照抄 vision.proto 的形态（GetInfo + 控制 unary + 事件 stream），**只改语义**：

```protobuf
syntax = "proto3";
package diagnosis;
option go_package = ".;diagpb";
import "google/protobuf/timestamp.proto";

service VibrationDiagnosis {
  // 能力握手：版本、已加载模型、支持的算法、契约版本
  rpc GetInfo (InfoRequest) returns (InfoReply);

  // ① 同步诊断：daqgate 把一窗数据带来，Python 算完就回（无状态，主力接口）
  rpc DiagnoseFeatures (FeatureWindow) returns (DiagnosisResult);
  rpc DiagnoseWaveform (WaveformWindow) returns (DiagnosisResult);   // 轨B

  // ② 异步事件流：Python 侧持续判定（如趋势外推、劣化预警）主动推
  rpc StreamAlerts (StreamRequest) returns (stream DiagnosisAlert);

  // ③ 基线管理：daqgate 下发"这段时间是正常运行"，Python 学基线
  rpc TrainBaseline (BaselineRequest) returns (BaselineAck);
  rpc GetBaseline   (AssetRef)        returns (BaselineInfo);

  // ④ 配置下发：阈值、ISO 机组类别、启用哪些算法（配置以 daqgate 为准）
  rpc ApplyAssetConfig (AssetConfig) returns (Ack);
}

// ── 输入：一窗特征值（轨A）──
message FeatureWindow {
  string asset_id   = 1;              // 设备/测点，daqgate 的实体 id
  repeated Sample samples = 2;        // 一段时间的采样（如最近 60s = 120 个点）
  AssetMeta meta    = 3;              // 转速/功率/支承类型/额定值
}
message Sample {
  google.protobuf.Timestamp ts = 1;   // ★真实采样时刻，不许推算
  map<string, double> values = 2;     // vel_x/vel_y/vel_z/acc_*/disp_*/freq/temp
  map<string, uint32> quality = 3;    // ★每通道质量码，复用 daqcontract StatusCode
}

// ── 输入：一帧波形（轨B）──
message WaveformWindow {
  string asset_id = 1;
  google.protobuf.Timestamp start_ts = 2;
  double sample_rate = 3;
  double rpm = 4;
  map<string, DoubleArray> channels = 5;   // "x"/"y"/"z" → 样本序列
  AssetMeta meta = 6;
}
message DoubleArray { repeated double v = 1 [packed=true]; }

// ── 输出：诊断结论 ──
message DiagnosisResult {
  string asset_id = 1;
  google.protobuf.Timestamp ts = 2;
  string engine = 3;                  // "rule"|"mlp"|"anomaly"|"llm-basic"|"llm-deep"|"fallback"
  string top_fault = 4;               // 闭集：正常/不平衡/不对中/轴承故障/机械松动/润滑异常
  map<string, double> scores = 5;
  double confidence = 6;
  string iso_zone = 7;                // A/B/C/D
  double health_score = 8;
  double anomaly_score = 9;
  repeated string support = 10;       // 支持证据
  repeated string conflict = 11;      // 矛盾/证据不足声明 ★不许省
  repeated string recommended_checks = 12;
  string summary = 13;
  bool degraded = 14;                 // LLM 不可用→本地规则回退时置 true
  map<string, double> derived_points = 15;  // 要回流成测点的派生量
}

message DiagnosisAlert {
  string asset_id = 1;
  google.protobuf.Timestamp ts = 2;
  enum Level { INFO=0; WARN=1; ALARM=2; }
  Level level = 3;
  string title = 4;
  DiagnosisResult detail = 5;
}
```

**与 vision.proto 的一致性**：同样是 Python Server / Go Client、同样 unary 控制 + stream 事件、
同样"配置以 daqgate 为准、Python 不持久化配置"、同样同机 unix socket / 分机 TCP+mTLS。

### 4.4 数据怎么到 Python（三选一，建议第 1 种）

| 方案 | 描述 | 评价 |
|---|---|---|
| **① daqgate 带数据来**（推荐） | daqgate 从 hs 查窗口 → 放进 `DiagnoseFeatures` 请求 | ✅ Python 零数据依赖、无状态、易测；Python 不需要知道 hs 存在 |
| ② Python 经 daqgate 反查 | Python 调 daqgate 的查询 gRPC | △ 反向依赖，链路变环 |
| ③ Python 直连 hs | Python 自己查 historystore | ❌ 破坏分层；且要处理 globalId 映射（见预研文 §6.2） |

**方案 ① 顺带解决了预研里那个 "globalId vs tag 语义" 的硬冲突**——
Python 根本不查库，就不存在 measurement 语义问题，映射完全由 daqgate 内部消化。

### 4.5 结论怎么回流（VQT 铁律）

诊断结果不是"打个日志就完了"，要变成**可趋势、可报警、可上云的测点**：

- daqgate 收到 `DiagnosisResult` → 在 `domain/`+`tagpoint/` 建虚拟设备测点：
  `health_score`、`anomaly_score`、`iso_zone`、`top_fault`、`confidence`、`days_to_threshold`
- **V/Q/T 三元组必须完整**：
  - **T** = 被诊断数据窗口的**真实结束时刻**（不是诊断计算完成时刻）
  - **Q** = 复用 daqcontract 的 `StatusCode`：LLM 降级/证据不足 → 标 `Uncertain` 而非 `Good`
  - **V** = 数值
- 这些测点随现有 adapter 上云，与 Modbus 采集来的原始量走同一套管线

## 5. 落地顺序（对齐视觉计划的阶段划分）

| 阶段 | 做什么 | 验收 |
|---|---|---|
| **D0 定契约** | 落定 `diagnosis.proto` v1，双端 codegen 过 | Go/Python 都能生成桩 |
| **D1 空跑骨架** | Python 起 Server，`DiagnoseFeatures` 返回**假结论**；daqgate `channel/diagnosis` 连上 | grpcurl 能调通，daqgate 日志见结论 |
| **D2 真数据打通** | 现场 SVT10 → G770 → daqgate Modbus 采集 → 写 hs → daqgate 取窗口调 Python | hs 里能查到振动测点，Python 收到真值 |
| **D3 轨A 算法** | ISO 分区 + 基线 + 趋势 + 异常检测（**先不接 LLM**） | 人为敲击/加负载 → anomaly_score 抬升、ISO 跳区 |
| **D4 结论回流 ⭐** | 结论建成虚拟测点，daqgate Web 出诊断视图 + 报警 | 端到端：振动异常 → Web 告警 → 上云 |
| **D5 证据包 + LLM** | 接规则/kNN/LLM 解释层，带降级 | 给出中文结论 + 建议检查项 + 证据不足声明 |
| **D6 轨B 波形** | 换硬件后接 `DiagnoseWaveform`，复用 signal_processing | 频谱/包络/阶次诊断上线 |

**先做 D1–D2 的空跑与打通，再灌算法**——和视觉计划"先通管道，再灌数据"同一条心法。

## 6. 风险与待确认

| # | 事项 | 说明 |
|---|---|---|
| 1 | ~~现场传感器型号未确认~~ | **2026-08-12 已核实并选定 WT-VB02-485**（见 §1.3/§1.4）。有人 SVT10 与郎汉德 LH-ST-485 因只出标量特征值被排除；一手资料存档在 [`doc/传感器资料/`](传感器资料/) |
| 2 | ★ **VB02 精度是否够 ISO 分级** | `<F.S±4%`，若速度量程固定 600 mm/s 则误差 ±24 mm/s，会淹没 ISO 判据线（2.8/7.1/18）。**这是当前唯一可能推翻选型的风险，必须先上台架标定。** 若不达标，第一顺位替代是维特 WT-VB05 / VB05D |
| 3 | ★ **能量寄存器无量纲** | 0x6E~0x9A 手册只给 `=((H<<8)\|L)`，无单位无缩放。做相对趋势不受影响，**做绝对判据必须先标定** |
| 4 | VB02 温度是芯片温度 | 非接触温度，**不能当轴承温度用**。温升类判据要么放弃，要么另配温度测点 |
| 5 | `ERRX/Y/Z` 故障诊断寄存器位定义未公开 | 手册表格是空的，需向厂家索要。拿到后可作为独立证据源并入证据包 |
| 6 | **hs 结构化记录契约未定** | 见 §2.5。**不在第一阶段关键路径上**（阶次能量用普通标量测点即可），但轨 B 取 `RAWFIFO` 波形帧前必须定 |
| 7 | ~~usr.cn wiki 页抓不到~~ | 已解决：该 wiki 是 JS 渲染 SPA，抓取工具拿不到，**必须用浏览器打开**；PDF 直链见 [`doc/传感器资料/README.md`](传感器资料/README.md) |
| 8 | ISO 分级要设备参数 | 功率等级、刚性/柔性支承——**必须由 daqgate 实体管理提供**，属于台账字段，需扩 EntityConfig |
| 9 | 转速从哪来 | 不平衡判据与阶次基频都依赖转速；VB02 的 `0x2A BASEBAND` 需要人工配基频，**能否自动跟随转速需确认**；三轴"振动频率"值能否当转速用需实测 |
| 10 | LLM 出公网 | 矿山/工厂现场大概率禁止。需准备本地小模型或"无 LLM 也能出结论"的降级路径（轨 A ①②③ 本来就不依赖 LLM，这点是优势） |
| 11 | 基线怎么确认"正常" | 需要人工确认一段"设备健康"的时间窗，是产品流程问题不是算法问题，daqgate 侧要出交互 |
| 12 | 诊断能力上限要对客户讲清 | 必须对客户明确：**这个硬件配置做的是"劣化预警"，不是"零件级故障定位"** |
