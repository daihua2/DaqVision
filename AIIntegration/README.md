## 5. 接入 historystore 的既有机制（2026-09-10 现场核实，非纸面）

选了"甲"之后，路径比预期现成得多 —— **不需要求 daqgate 发 guid 或证书**：

| 环节 | 机制 | 出处（AISERVER 实测） |
| --- | --- | --- |
| **写值** | `rpc PostVQT(daq.VQTs) returns (daq.Status)` | `historystore/proto/historystore.proto` |
| **声明结论点** | `rpc PushEntityConfigs(stream EntityConfigPush)` —— 边缘主动推，载荷**不带 guid**，归属由 hs 按连接的 peer cert 定 | 同上 |
| **身份** | mTLS 客户端证书的 SAN URI `urn:daqgate:guid:<uuid>`，hs 的 `GuidFromCert` 从中剥 guid；**证书就是身份，应用层不能自报** | `AICloud/AIBackend/irtdb/cert.go` |
| **签发** | AICloud 用自己 `cert/` 下的 `protocolCA.cer` + `ca.key` 直接签客户端证书，与 daqgate 同一套 CA | 同上；两文件已确认在 `/home/Project/AICloud/AIBackend/cert/`（`ca.key` 600） |
| **自动成为实体** | AICloud 对账器每分钟扫镜像，出现的任何 guid 自动建成实体，落 网关管理(58) 下、默认仅管理员可见、**绝不自动删** | `AICloud/AIBackend/irtdb/gatewayentity.go` |
| **可挂自述属性** | `GatewayIdentity.attrs` 是 `map<string,string>`，hs **只搬运不解释**、原样在 `ListEntityIdentities` 回 | `historystore.proto` |

> 它不是网关（没有采集连接/采集通道），语义错位。`attrs` 那个自由 map 是现成的分流钩子，
> 但要不要用、由谁改对账器，待定。

## 6. ★为什么只有骨架进程能连 hs（不是洁癖，是会炸）

「域跑各自的 worker 进程」+「一份 guid、一张证书」这两句并排放，很容易读成
"每个 worker 各自拿着那份身份去连 hs"。**那个读法会互相删点，而且是循环的。**

`historystore.proto` 已钉死的三条语义：

- ② **同一 guid 并发两条流：后到者胜，先到的那条被 hs 主动关（CANCELLED）**；
- ③ `SNAPSHOT_BEGIN…END` 之间断流 = **半份快照**，hs 丢弃并保留旧快照，重连必须**重推全量**；
- `SNAPSHOT_END` = **原子提交，本轮未出现的旧实体一律删除**。

于是域 A、域 B 各推自己那批点：B 建流踢掉 A → A 半份快照被丢 → B 提交时 A 那批点
"本轮未出现"**被全删** → A 重连重推，轮到 B 被踢。**两边轮流删对方的点。**

★这不是 hs 的缺陷：那三条是为"**一个 guid = 一个配置源**"设计的。是"多进程共用一份身份"与它冲突。

⇒ **骨架单进程统一对 hs**：汇总成**一份**快照、**一条**流、**一个**连接写 VQT。
worker 只吃数据出结论，交回骨架。容量无虑 —— 单 guid 快照上限 200 万实体
（`kMaxSnapshotEntities`，注释：上限只为防跑飞，单网关几十万点是常态）。

> 由 AICloud `C-9 §3` 提问触发。设计本来如此（《骨架与算法模块分界》里"身份与连接"
> 与"结论回流"从一开始就在骨架那八件里），**是措辞漏了这层**——但措辞能让人读出一个会炸的
> 实现，就是措辞的问题。

### 8.1 第一个域检验了"丢一个 `.py` 就多一个域"

本域**没有**让骨架为它加任何分支：装载、取数、成帧、点位分配、回流、调度、对外口全走既有的路。
用例是拿**真的装载器扫真的 `domains/` 目录**装进来跑的 —— "能不能只靠一个文件长出一个域"
这件事本身被钉住了。

★骨架这轮确实动过一处（见 §8.2），但那是**所有域都会撞上**的通用缺口，不是为本域开的口子。

### 8.2 由它逼出来的两处骨架缺口（已补，契约升 1.1）

| 缺口 | 补法 | 为什么不能绕 |
| --- | --- | --- |
| **绑定没有台账参数位** | `Binding.params` + `DomainInfo.params`/`ParamSpec`（契约 1.1） | ISO 判级的边界取决于机组类别与支承方式；轴向是哪根轴决定"不对中还是不平衡"。这些是**每台机器一份的静态事实**，没有时刻也没有质量码 —— 绑不到测点上，往库里塞个恒定值的点就是把台账伪装成测量 |
| **质量码里没有"配置不全"这一档** | 新增 `Quality.CONFIG_INCOMPLETE`（出向仍映射既有 `OutOfService`，**不发明新 StatusCode**） | 与 `INPUT_BAD` 混一起，现场只会往设备上查，而真相是没人填过这台机器的台账 |

★台账参数**骨架只搬运不解释**（照 hs 的 `GatewayIdentity.attrs`）：键名与取值由域在
`Declaration.params` 里自述，AICloud **按自述渲染表单** —— 与能力位同一条道理，新增域两侧都不改。

### 8.3 ★这个域**不移植** v5 的阶次诊断，理由是它在现场没有输入

原 v5 的招牌是 **阶次幅值 1X~5X + 规则卡 + MLP 工件**（`backend/order_diagnosis/`）。
2026-09-11 读源码确认：它喂的是 `services/acquisition.py::simulate_frame` **造的仿真波形**，
不是 hs 的点。而《算法侧改造方案》§1.5.2 已逐款核实六款 Modbus 振动传感器
**无一家给谱线数组** ⇒ 那套算法**现场无输入**。

⇒ 移过来就是第二个"跑得很热闹但没有真输入"的域（v4 已是先例）。等 L2 档的频带谱能量
（`_e_p1..p8`）真进了实时库，它作为**另一片**再落 —— 按同样的分界另丢一个 `.py`。

⇒ **v5 那条真有输入的路**是 `services/hs_realtime.py`：13 个标量点 → 人工标注 → XGBoost 分类。
它归本域的第 ② ③ 层（基线/趋势/异常检测），等"域私有状态"的落点定了再落。
★顺带记一条那边的病：`_to_float` 拿不到就给 `0.0` —— 在速度上 0 是**最好的读数**，
于是设备故障被读成运行完美。本域的 `_as_float` 是它的反面，且有变异用例钉着。

## 10. 训练执行（2026-09-11，契约 1.3）

`workbench.py` 先落的是任务表与五态机；`trainer.py` 是缺的那半 ——
取待跑任务、组装数据集、调模块的 `train()`、工件落盘。
算法模块那侧的三个类型（`Dataset` / `TrainedArtifact` / `ProgressSink`）在 `types.py`，
这补上了《骨架与算法模块分界》§6 待定第 1 条的后半。

### 10.1 五条形状

| # | 怎么做的 | 为什么 |
| --- | --- | --- |
| 1 | **任务，不是阻塞调用** | v5 是同步阻塞 + "请不要关闭页面"——那句话本身就是设计缺陷的自白：它把"这活儿跑得久"变成了用户的责任 |
| 2 | **串行一条，排队顺序 = 建任务顺序** | 单进程多域共享算力；两个训练同时跑会把**推理也拖卡**，而推理有节拍，卡了就掉数据。不做优先级——优先级要有人维护，且会让"我的任务为什么还没跑"变成查不清的问题 |
| 3 | **取不到数的样本不静默** | 样本记的是时间范围，训练时那段可能已被滚存删掉。丢了几条、为什么丢，写进任务 `message` **与工件 `meta_json`**（任务记录会被清理，而"这个模型用什么训的"要长久答得上） |
| 4 | **新工件不自动启用** | 自动启用 = 训一次就换一次现场模型，而训练常常只是拿新标注试试看 |
| 5 | **取消回执如实分三种** | 排队中的当场取消；**正在跑的只是"请求取消"**（模块不看取消标志就会跑完）；已终态的回"不适用"。谎报"已取消"会让界面说谎 |

★工件落盘走**临时文件再改名**：半个工件躺在那里，下载下来是坏的，而记录里看着一切正常。

### 10.2 验证

- **269 条单测全绿**（本轮新增 23 条）；
- **43 条变异验证全部变红**（本轮 12 条），钉的包括：不支持训练的域也照建任务、
  取不到数静默丢掉、一条都组装不出来也当成功、新工件自动启用、正在跑的谎报"已取消"、
  排队取最新的、窗口用错（拿绑定的 `window_sec` 而不是样本自己的时间范围）、
  工件不走临时改名、空工件放行、准确率越界放行。
- 整机用例加了一条：**用一个不支持训练的域去开训**，回的必须是"能力位里没有 train"
  而**不是**"未接训练执行器" —— 两句话区分得开，才证明 `service.py` 真把执行器装上了。

## 11. 低频振动第 ② 层：基线与偏离（2026-09-11）

第 ① 层判的是"绝对值该不该停机"（ISO 国标）；第 ② 层判的是
**"这台机器跟它自己好的时候比，变了没有"** —— 没有频谱时，这是判故障类型的主要抓手。

新增四条结论：`vel_z_max`（各轴相对基线的最大 z 分数）、`ratio_drift`（三轴比例漂移）、
`temp_rise`（温升）、`anomaly_score`（0~100，**排序用的分数，不是概率**）。

### 11.1 基线走**训练面**产出，落 `artifacts` 表 `kind='baseline'`

判据是 AICloud `C-11 §5` 给的：**要能看见"什么时候采的、能不能重采"的，就是资产**。
基线两样都要（换工况必须重采；"这条基线采自哪段"是判断结论可不可信的前提）
⇒ 它与模型同级，走同一条训练面、同一张工件表、同一个启用机制。

★由此逼出 `TrainedArtifact.kind`：**产出的是哪一类工件由域说了算**。
  骨架写死成 `model` 会让基线顶掉真模型的激活位（两者本该各占各的）。

四条采基线的纪律：

| 纪律 | 为什么 |
| --- | --- |
| **只用被标成"正常"的样本** | 拿故障数据采出来的基线会把故障态当成常态，**从此再也报不出这个故障** |
| 少于 5 帧**当场失败并说清** | 样本太少算出来的 σ 没有意义，而 σ≈0 的基线会让任何正常波动都变成"z 分数爆表" |
| σ 有下限 0.01 mm/s | 传感器分辨率决定 σ 不可能真是 0。不设下限的后果是天文数字的 z —— 比除零更坏，因为它看着像个结论 |
| 基线**没有"准确率"** | `accuracy=None`，不拿 1.0 顶（界面会把它显示成"100%"） |

基线本体是 JSON，**带格式版本**（`vibration_lowfreq/baseline@1`；★拆分后为 `vibration_baseline/baseline@1`，统计量改为中位数与四分位距，老格式拒读）：
将来改格式，老工件要能被认出来而不是被误读。格式不认就落坏码，不硬算。

### 11.2 ★骨架补的最后一格：推理时把「当前启用的工件」交给模块

模块不碰存储（分界文档 §1），但它要用自己训出来的东西。于是：

- `Frame.artifacts: dict[kind, ArtifactBlob]` —— 成帧时由 `artifactcache.ActiveArtifacts` 读好放进去；
- **按工件 id 缓存**（工件只增不改，同一个 id 就是同一份内容），有人点了"启用"下一拍就换过来；
- **没启用就没有这一档** —— 不给空的、更不"随便挑个最新的顶上"。顶上去的结论看起来完全正常，是最坏的一种；
- **记录说有启用件、磁盘上却没有 ⇒ 每周期都吵**：那是数据面与文件面对不上，比"没有模型"更需要有人看；
- ★**训练路径不带工件** —— 训的时候拿旧模型当输入，就是模型喂自己，漂了也看不出来。

### 11.3 ★为什么**趋势外推与剩余寿命**这一片不做（不是忘了）

★**2026-09-17 订正**：本节原先把 `ewma_trend` 与「剩余可用天数」当成一件事，
统一归因于"骨架没有跨帧状态那一格"。**这个归因对后半是错的** ——
读完 `weibull-knowledge-informed-ml`（论文级 RUL 实现）后查明：
**RUL 推理是逐帧无状态的**，龄期只在训练时进损失函数，前向传播里根本没有它。
详见 [`research/external-projects/README.md` §15](research/external-projects/README.md)（读源码的结论）
与 [`research/rul/README.md`](research/rul/README.md)（★**我方自己跑出来的数**：
标量做不了 RUL、原项目 test 标签错在哪、威布尔损失的"有效"依赖什么）。
**结论不变（两半现在都不做），但两半的理由必须分开写** ——
因为它们决定了该去争取什么：按旧理由该去改骨架，而改骨架对 RUL 一点用没有。

**前一半：`ewma_trend`（劣化速度、阈值穿越天数）—— 理由仍成立。**
它要的不是"这一帧"，是同一路输入在很多天上的走向。要做只有两条路，**现在都不该走**：

| 路 | 为什么现在不走 |
| --- | --- |
| 把绑定窗口拉到几十天 | 每拍取几十天的点只为算一个斜率 —— 把实时库当批处理引擎用 |
| 让模块自己攒跨帧状态 | 与分界直接冲突；且进程一重启就从头攒，界面上看不出"这条趋势从什么时候开始的" |

⇒ 等骨架真给"跨帧运行状态"或"长窗口取数"那一格时再做，而那一格应当由**真需求逼出来**
（就像台账参数 1.1、推理时的工件 本轮 那样）。在那之前**宁可少一条结论，
也不给一个每次重启就归零的"剩余可用天数"**：那种数字看起来最像专业结论，也最容易被当真。

**后一半：RUL（剩余寿命）—— ★卡点不在骨架，而关键路径今天就要动。**
用户已定调：**RUL 是要重点实现的**，并指出 **「现在没数据 ≠ 未来没数据」** ——
这一条推翻了本节初稿的落点。方法本身不需要骨架给新的一格；
真正要分清的是**哪些今天不做就补不回来**：

| 组 | 事项 | 何时做 |
| --- | --- | --- |
| ★**甲1** | **长期历史留存 / 归档策略** | ★★**今天**。实时库有滚存（现场已发生过"因存储阈值释放"）。RUL 要从投运到失效的整条轨迹，**历史被滚存吃掉就永远回溯不出来** |

## 12. 部署前自查（2026-09-11）—— 查出三处，全是"装上去才会炸"的那类

部署还在等授权（`AI-16 §3`），趁这个空档把"装到 AISERVER 上会怎样"逐条现查了一遍。
**三处都是单测全绿时一直在的**，其中两处要去目标机上现查才看得出来。

### 12.1 服务重启后，训练中的任务会永远挂在"训练中"

执行器只取 `pending`。进程在训练中途死掉（崩溃 / 断电 / `systemctl restart`）之后，
那条任务**永远停在 `running`**：没人跑它、也没人把它标失败，界面上一直显示"训练中"。

- **修**：`Trainer.start()` 先把遗留的 `running` 标成 `failed`，原因写明"服务重启时仍在训练中，未完成"，再开始取新任务。
- ★**标失败，不改回 `pending` 自动重跑**：半截训练可能正是把进程搞崩的那个（内存打爆之类），自动重跑就是自动再崩一次。重不重跑是人的决定。
- ★前提写进了代码：**本进程是这个库唯一的执行器**。将来多进程共用一个工作台库，这里会误杀别人正在跑的任务，那时要换成租约。
- 用例 3 条（遗留 running 标失败 / 遗留 pending 照常跑 / 终态不碰），变异 3 条全红。

## 14. 视觉域落地：安全帽检测 + 事件驱动入口（2026-09-11，契约 1.4）

用户定视觉域走 **CPU + onnxruntime，不拖 torch**。可行性证明在 `research/vision-onnx-parity/`
（与现网 ultralytics 24 组逐位一致）；本节是落成域本体。

### 14.1 为什么骨架要动：两种完全不同的输入形态

| | 振动域（测点） | 安全帽（图片） |
| --- | --- | --- |
| 输入 | 测点，绑 globalId | 一张图片，**不绑测点** |
| 谁发起 | 骨架按节拍**去取** | 现场**送来**，来一张算一次 |
| 结论时刻 | 样本时刻 | **拍照时刻**（调用方给） |

### 14.2 骨架补的几样（`AI-13 §3` 许下的"非测点输入源"那一类，由真域逼出来了）

| 补了什么 | 说明 |
| --- | --- |
| `InputSpec.kind` | `point` / `image`。显式声明，不靠"roles 里没写就是图片"这种约定让骨架猜 |
| `InputBlob` + `Frame.blobs` | 非测点输入。`t` 是采集时刻，**没有缺省、必须带时区** |
| `events.py`（`EventRunner`） | 校验 → 成帧 → 交给域 → 回流。不含图片解码与算法（那是域的事） |
| HTTP `POST /infer/{域}/{绑定}` | 图片是大对象，按 C-8 走 HTTP。正文原始字节；`X-Captured-At` 必填 |
| 调度器 | **纯图片域不起轮询线程**（起了的样子是每拍拿空帧推理、落一串"没数据"）；结论点照建 |
| `BindingStore.put(allow_no_roles=)` | 只有**全部输入都是图片**的域才放行空 roles —— 由知道域声明的 api 层决定，存储层不放宽 |

四条纪律：

1. **拍照时刻没有缺省**：巡检拍完可能半小时后才上传，拿上传时刻当 T 就是把"半小时前的违规"记成"现在的违规"；
2. **没有绑定不收**：台账（阈值）与结论点都挂在绑定上，没有就只能猜；
3. **只读运行如实说没写**（`written=false` + `write_note`），写失败也不吞推理结果；
4. **忙了明说 503**，不无限排队（同机还有有节拍的测点推理，卡了会掉数据）。

★**Python 3.10 的坑**：标准库 `datetime.fromisoformat` 在 3.10 上**不认末尾的 `Z`**（3.11 起才认），
而现场正是 3.10。不手工换，最常见的 `...T01:30:00Z` 在现场会被拒。已兼容，且有一条**只在 3.10 上才会红**的变异钉着。

3. **域先校验**（可选钩子 `validate_artifact(kind, blob) -> (拒收原因, 事实)`）：不过 422，校验本身抛异常也算不过；
   域没提供校验照收，但回执 `validated=false` 明说。域读出的事实（模型元数据里的描述/版本/许可/类别表）**原样存进工件** ——
   "文件名 yolo11n、元数据写 YOLOv5n"这种不一致就留在记录里看得见。
4. **不自动启用**。同一文件（域+种类+sha256）重复导入 409 并指明已有工件。

### 16.2 为什么只走服务进程

工作台库"服务进程是唯一写者"（训练执行器重启时据此收拾遗留任务）。所以导入只有一个口：
HTTP `POST /artifacts/import/{domain}?name=…&source=…&training_data=…&license=…`，正文是工件字节；
命令行 `python -m aiintegration.admin import-artifact|list-artifacts|activate-artifact` **只是这个口 / 控制面的客户端**，
不开库。`activate-artifact` 必须带 `--yes`。

### 16.3 训练产出也补上来历

`trainer._store` 由骨架写 `origin=trained`、`source=训练任务 N`、`training_data=训练集名 + 样本数 + 标签分布 + 跳过数` ——
训练产出的来历本系统**确实知道**，不靠域自觉。

★**老库补列**：`CREATE TABLE IF NOT EXISTS` 对已存在的表一个字都不改，新列不会自己长出来 —— 读的时候才 `no such column`，
而且是在现场（AISERVER 上就有一份 1.4 时代的库）。`Workbench._migrate()` 开库即补四列；老工件按训练集号回填一句
"训练集 id=N（1.5 之前产出，未记录详情）"，**不编造细节**。

## 17. 训练数据的来源性质，与「停用工件」（2026-09-16，契约 1.6 / 1.7）

### 17.1 为什么要有 `data_origin`

2026-09-16 训出的第一条基线**采自实时库的仿真信号**（AICloud `C-35 §4.4`），而"它是仿真的"当时只记在
**工件名、训练数据说明、十条标注备注**三处 —— 全是**给人看的字符串**。字符串一改名就断，
而「这条结论是不是拿仿真数据训出来的」恰恰是**要挡在人眼前的判据**。AICloud `C-36 §4` 据此请我方立成字段。

这一格只回答一件事：**这条结论能不能用来说现场设备的话。** 它**不是工件的好坏** ——
`simulated` 不是"差的工件"，跑链路、做回归都该用它。

### 17.2 ★记在**绑定**上，不记在每条标注上（2026-09-16 用户裁定）

AICloud 只提了工件那一格。我方指出：**只加工件那一格，"仿真与否"仍要靠人在训练那一刻填一句**，
那还是靠自觉，只是把自觉从工件名挪到了新字段上 —— 而这正是对方发函要消灭的东西（`C-37 §2` 认下这一点）。

**仿真与否是点的性质**：绑的那组点接的就是仿真信号源，与人框了哪一段无关。

| 层 | 字段 | 谁写 |
| --- | --- | --- |
| 绑定 | `Binding.data_origin = 9` | AICloud 可写（配绑定时选） |
| 样本 | `samples.data_origin`（库内，不进契约） | 骨架在**入集那一刻从绑定取快照** |
| 工件 | `Artifact.data_origin = 22` | 骨架写，**只读**；按参与训练的样本**取最严** |

★**快照不被反写**（照 `samples.label` 那条既有规矩）：日后真机接入、绑定改成 `field`，
**当初用仿真数据训出来的工件岿然不动**。

### 17.3 三条语义（`dataorigin.py` 收口）

1. **空 ≠ 现场。** 老绑定/老样本/老工件补列一律补空，界面显示「未声明」。
   我方把它推到更严的一条：**只有明写 `field` 才算现场** ⇒ "现场 + 未声明"混在一起时，
   工件那一格**退回未声明，而不是现场**（"大部分是现场所以算现场"是这类字段最容易出的默认）。
2. **取最严。** 任一样本 `simulated` ⇒ 工件 `simulated`；混了多少比例写进 `training_data`。
   取不到数、没参与训练的样本**不计入** —— 它没进模型，就影响不了这个工件能不能说现场的话。
3. **不是封闭枚举。** 骨架碰到不认得的取值**原样透传**，不吞、不纠错。

★**不做自动回填，但留一条只朝严的兜底**：按绑定"现在"的取值回填历史样本，方向是错的
（日后改成 `field` 会把历史工件洗成现场）。所以老样本就是未声明。
但 `dataorigin.effective()` 留了一条：**快照为空 + 绑定现在说 `simulated` ⇒ 按 `simulated` 计**；
绑定说 `field` 或没说则**仍是未声明**。⇒ 这条兜底**不可能产出一个假的 `field`**，
只可能把"不知道"抬成"仿真"（用穷举钉成了用例）。现役那条基线正是靠它在重训后拿到 `simulated`，
**不必伪造历史快照** —— AICloud `C-38 §2` 把样本那一栏也查了一遍，确认是兜底拿到的、不是回填。

### 17.4 ★1.7「停用工件」：现场撞出来的缺口，不是设计推演

重训基线时 `StartTraining` 的 `binding` 传了空串 ⇒ 工件落成**"全域通用"**（`binding=''`）并被启用。
改对重训之后要退掉它，结果**退不掉**：

- `ActivateArtifact` 只让**同作用域**(域,种类,对象)的旧件让位 ⇒ 同作用域里没有别的件能顶掉它；
- `DeleteArtifact` **拒删激活中的**（这条本身是对的）。

⇒ **作用域本身建错的件，此前永远取消不掉。** 这个缺口在作用域正确时看不出来 ——
启用新件顺手就把旧件顶掉了，没人会发现"顶不掉"的情形存在。

**危害是静默的**：`artifactcache.for_binding()` 找不到对象专属件时**会回退捡全域通用件**（刻意设计的，
注释写着"`binding=''` 是**显式声明过**的全域件" —— 问题恰恰在于那一件不是显式声明的）。
⇒ 该域**任何新建的、自己还没训过基线的绑定**，会静默套用另一台机组的仿真基线出第②层结论，
而本该出现的 `MODEL_NOT_LOADED(-1034)` 不会出现。

★AICloud `C-38 §3` 独立发现了这两个启用行，但判断我方"没有回退路径、哪天有谁加一条才会出事"——
**我方 `AI-39 §2` 往更严重的方向订正了他们**：路径今天就有。他们看对了形状，少的那块料只有我方有。

**补法**：`rpc DeactivateArtifact (IdReq) returns (MutateRes)`（纯加方法，不动任何字段编号）
+ 命令行 `deactivate-artifact --id N --yes` + `list-artifacts` 显示来源那一列
（**空显示「未声明」而不是留白** —— 留白会被当成"这项没问题"）。
★停用后该对象没有可用工件，结论会落 `-1034`，**这是对的**：没有基线就该说没有基线。

## 19. ★术语：界面说「模块」，代码说「域」（2026-09-17 用户裁定）

**这是一条刻意的双轨，不是历史遗留，请勿"统一"掉。**

| 场合 | 用词 |
| --- | --- |
| **AICloud 界面**、面向用户与业务的文档、往来函里谈业务时 | ★**模块** |
| 代码标识符（`domains/`、`Domain` 基类、`aiintegration.domains`、变量 `domain`） | **域**，保留现状 |
| **契约字段**（`DomainInfo`、`ListDomains`、`Binding.domain`、`Artifact.domain`…） | **域**，保留现状 |

### 为什么这么定

- **"模块"是原始用词**：分界文档本来就叫《骨架与**算法模块**分界》；"域"是后来在代码里引入的。
  用户的原话也是「AI 服务是以**算法模块**运行的」⇒ 面向人的那一侧回到"模块"。
- **但改代码与契约不值**：契约字段名一变，AICloud 的生成码、桥上那几个方法、界面绑定**全要同步改**，
  且必须两侧同时发版 —— 而这是**纯话语问题，不影响任何语义**。
  在对方正做界面重构时塞一个破坏性变更，是给别人添乱。
- ⇒ **界面改词零成本，代码不动零风险。** 双轨的代价只有一条：要有人把它写下来，就是本节。

### 落实

1. **我方文档与往来函**：谈业务时用"模块"；引用代码或契约字段时保留原名（如 `DomainInfo`），不翻译。
2. ★**AICloud 界面要显示"模块"** —— 他们正在做以设备为中心的配置界面，**这条要让他们知道**。
3. **契约注释**：下次因实质改动升版时（`DomainInfo.category` / `ParamSpec.level` / 列表 `bindings` 过滤那几条已排队），
   顺带在 `DomainInfo` 上加一句「界面上呈现为『模块』」。
   ★**不为一句注释单独投分发点** —— 那会让对端多做一次无谓的核对（`AI-41 §2.3` 已与对方约好：投产时点跟着他们的阶段走）。

★**一句话记住**：`domain` 是这个东西在代码里的名字，「模块」是它在人面前的名字。**同一个东西，两个名字，故意的。**

## 20. 停机判定（2026-09-18，定案 1.6 / 2.5 —— R1）

来由是借鉴平台：它用启停表达式判运行/停机/未知，停机数据不进统计、不出诊断
（见 [doc/借鉴平台振动诊断编排与设置.md](doc/借鉴平台振动诊断编排与设置.md) §4、§7.2）。
我方此前**没有运行状态这回事**：停机时的振动照常判级、照常进基线 —— 后者会把"停着"当成常态，
开机后每一拍都显得偏高，而且看不出来是配置问题。

做法比平台简单一档（用户 2026-09-18 定）：

| 事项 | 结论 |
| --- | --- |
| 怎么判 | 模块 1、2 的诊断上各加可选参数 `stop_threshold`（速度有效值 mm/s）。**三轴速度最大值 < 门槛 ⇒ 停机**；不填不判 |
| 有没有缺省 | **没有**。按设备自己定，填错由用户负责（不做自动识别，见 [doc/暂缓与未定事项.md](doc/暂缓与未定事项.md)） |
| 停机时怎么写结论 | 新增结论点 `run_state`（运行 / 停机 / 未判）。文字点写「停机」（烈度区、方向性提示），烈度区数值写 **0**；**数值类结论这一拍不写** |
| 为什么数值点不写 | 实时库的状态码里**没有**「设备停机、此值不适用」这种点值语义（`Stopped 8011` 是操作状态族，按 §15 的规矩不许挪用）。落坏质量会在界面上显示成"坏值"，而停机不是坏 ⇒ 点上保留停机前最后一值及其时刻，界面凭 `run_state` 置灰 |
| 采基线 | **剔除停机帧**；剔完不足 5 帧则训练失败，并说清剔了几帧。门槛非法时**不采**（判不了哪些帧是停机） |
| 门槛非法（非正数） | 只让 `run_state` 落 `CONFIG_INCOMPLETE`，烈度分级等照出 |

★两个模块各有一份 `run_state()`（**域之间互不 import**，分界文档的规矩）。
  两份判法必须逐条相同，由 `test_domain_vibration_baseline.test_与模块1判法一致` 钉住 —— 拿两份实现互为判据，
  比两边各写一遍断言更能挡住"改了一边忘了另一边"。

⇒ **这一条要告知 AICloud**：新增 `run_state` 结论点、`iso_zone_code` 多了取值 0、
  界面需要凭 `run_state` 把停机时的数值置灰（否则界面会显示成"停机时数值一直不动"）。
  与 U6 / U8 那批一起发（发函前仍须用户同意）。

### 20.1 顺带查实的一处竞态：已训完的任务被回成"已请求取消"

新增用例改变了整机时序，把 `trainer.cancel()` 的一个窗口撞出来了（3.12 环境全量跑里红）：
执行器**先写终态、后在 `finally` 里清 `_current`**，两步之间取消，会按 `_current` 判成"正在跑"，
回一句"已请求取消；…会跑完当前这次训练才停" —— 而那次训练**早已结束**，谎报了一次不会发生的取消。

改法：`cancel()` **先按库里的状态判终态**（`ready` / `failed` / `canceled` 一律回"取消不适用"），
不看 `_current`。任务的终态以库为准，与执行器线程的清理次序无关。
用例把那个窗口直接构造出来（写完终态后手工把 `_current` 摆回去）而不是靠时序碰运气。
