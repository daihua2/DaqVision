## 5. 接入 historystore 的既有机制（2026-09-10 现场核实，非纸面）

选了"甲"之后，路径比预期现成得多 —— **不需要求 daqgate 发 guid 或证书**：

| 环节 | 机制 | 出处（AISERVER 实测） |
| --- | --- | --- |
| **写值** | `rpc PostVQT(daq.VQTs) returns (daq.Status)` | `historystore/proto/historystore.proto` |
| **声明结论点** | `rpc PushEntityConfigs(stream EntityConfigPush)` —— 边缘主动推，载荷**不带 guid**，归属由 hs 按连接的 peer cert 定 | 同上 |
| **身份** | mTLS 客户端证书的 SAN URI `urn:daqgate:guid:<uuid>`，hs 的 `GuidFromCert` 从中剥 guid；**证书就是身份，应用层不能自报** | `AICloud/AIBackend/irtdb/cert.go` |
| **签发** | AICloud 用自己 `cert/` 下的 `protocolCA.cer` + `ca.key` 直接签客户端证书，与 daqgate 同一套 CA | 同上；两文件已确认在 `/home/Project/AICloud/AIBackend/cert/`（`ca.key` 600） |
| **自动成为实体** | AICloud 对账器每分钟扫镜像，出现的任何 guid 自动建成实体，落 网关管理(58) 下、默认仅管理员可见、**绝不自动删** | `AICloud/AIBackend/irtdb/gatewayentity.go` |
| **可挂自述属性** | `GatewayIdentity.attrs` 是 `map<string,string>`，hs **只搬运不解释**、原样在 `ListEntityIdentities` 回 | `historystore.proto` |

> ⚠️ 由此引出的下一个待议点：对账器会把 AIIntegration 建成**"网关"实体**。
> 它不是网关（没有采集连接/采集通道），语义错位。`attrs` 那个自由 map 是现成的分流钩子，
> 但要不要用、由谁改对账器，待定。

## 6. ★为什么只有骨架进程能连 hs（不是洁癖，是会炸）

「域跑各自的 worker 进程」+「一份 guid、一张证书」这两句并排放，很容易读成
"每个 worker 各自拿着那份身份去连 hs"。**那个读法会互相删点，而且是循环的。**

`historystore.proto` 已钉死的三条语义：

- ② **同一 guid 并发两条流：后到者胜，先到的那条被 hs 主动关（CANCELLED）**；
- ③ `SNAPSHOT_BEGIN…END` 之间断流 = **半份快照**，hs 丢弃并保留旧快照，重连必须**重推全量**；
- `SNAPSHOT_END` = **原子提交，本轮未出现的旧实体一律删除**。

于是域 A、域 B 各推自己那批点：B 建流踢掉 A → A 半份快照被丢 → B 提交时 A 那批点
"本轮未出现"**被全删** → A 重连重推，轮到 B 被踢。**两边轮流删对方的点。**

★这不是 hs 的缺陷：那三条是为"**一个 guid = 一个配置源**"设计的。是"多进程共用一份身份"与它冲突。

⇒ **骨架单进程统一对 hs**：汇总成**一份**快照、**一条**流、**一个**连接写 VQT。
worker 只吃数据出结论，交回骨架。容量无虑 —— 单 guid 快照上限 200 万实体
（`kMaxSnapshotEntities`，注释：上限只为防跑飞，单网关几十万点是常态）。

> 由 AICloud `C-9 §3` 提问触发。设计本来如此（《骨架与算法模块分界》里"身份与连接"
> 与"结论回流"从一开始就在骨架那八件里），**是措辞漏了这层**——但措辞能让人读出一个会炸的
> 实现，就是措辞的问题。

### 8.1 第一个域检验了"丢一个 `.py` 就多一个域"

本域**没有**让骨架为它加任何分支：装载、取数、成帧、点位分配、回流、调度、对外口全走既有的路。
用例是拿**真的装载器扫真的 `domains/` 目录**装进来跑的 —— "能不能只靠一个文件长出一个域"
这件事本身被钉住了。

★骨架这轮确实动过一处（见 §8.2），但那是**所有域都会撞上**的通用缺口，不是为本域开的口子。

### 8.2 由它逼出来的两处骨架缺口（已补，契约升 1.1）

| 缺口 | 补法 | 为什么不能绕 |
| --- | --- | --- |
| **绑定没有台账参数位** | `Binding.params` + `DomainInfo.params`/`ParamSpec`（契约 1.1） | ISO 判级的边界取决于机组类别与支承方式；轴向是哪根轴决定"不对中还是不平衡"。这些是**每台机器一份的静态事实**，没有时刻也没有质量码 —— 绑不到测点上，往库里塞个恒定值的点就是把台账伪装成测量 |
| **质量码里没有"配置不全"这一档** | 新增 `Quality.CONFIG_INCOMPLETE`（出向仍映射既有 `OutOfService`，**不发明新 StatusCode**） | 与 `INPUT_BAD` 混一起，现场只会往设备上查，而真相是没人填过这台机器的台账 |

★台账参数**骨架只搬运不解释**（照 hs 的 `GatewayIdentity.attrs`）：键名与取值由域在
`Declaration.params` 里自述，AICloud **按自述渲染表单** —— 与能力位同一条道理，新增域两侧都不改。

### 8.3 ★这个域**不移植** v5 的阶次诊断，理由是它在现场没有输入

原 v5 的招牌是 **阶次幅值 1X~5X + 规则卡 + MLP 工件**（`backend/order_diagnosis/`）。
2026-09-11 读源码确认：它喂的是 `services/acquisition.py::simulate_frame` **造的仿真波形**，
不是 hs 的点。而《算法侧改造方案》§1.5.2 已逐款核实六款 Modbus 振动传感器
**无一家给谱线数组** ⇒ 那套算法**现场无输入**。

⇒ 移过来就是第二个"跑得很热闹但没有真输入"的域（v4 已是先例）。等 L2 档的频带谱能量
（`_e_p1..p8`）真进了实时库，它作为**另一片**再落 —— 按同样的分界另丢一个 `.py`。

⇒ **v5 那条真有输入的路**是 `services/hs_realtime.py`：13 个标量点 → 人工标注 → XGBoost 分类。
它归本域的第 ② ③ 层（基线/趋势/异常检测），等"域私有状态"的落点定了再落。
★顺带记一条那边的病：`_to_float` 拿不到就给 `0.0` —— 在速度上 0 是**最好的读数**，
于是设备故障被读成运行完美。本域的 `_as_float` 是它的反面，且有变异用例钉着。

| ① | **标注 ≠ 样本** | 标注是"人对一段数据的判断"，样本是"进了某个训练集的那份拷贝"。分开才谈得上"同一段数据进了三个训练集" |
| ② | **移出 ≠ 删除** | 把数据从训练集拿掉，与否定人当初的判断，是两件完全不同的事（v5 特意分开的，保住） |
| ③ | **标签不枚举** | 没有标签表 —— 有表就一定有人去维护它，也一定漂。新标签用一次就存在 |
| ④ | **训练是任务不是阻塞调用，且终态不可覆盖** | v5 是同步阻塞 +"请不要关闭页面"。已失败的任务被改成"就绪"，界面上就再看不出它失败过 |

★外加我方一条：**样本上的标签是入集那一刻的快照**，不跟随标注改动 ——
否则"这个模型当初是用什么训的"就没有答案了。

### 9.2 ★两件**故意没开**的（不是遗漏）

1. **`StartTraining`** —— 训练执行还没落（要先定 `Dataset`/`Artifact` 怎么交给算法模块，
   以及数据集怎么从实时库组装）。任务表、状态机、工件表都已就位，故查询那几口现在就能接。
   **不给一个永远 pending 的 `StartTraining`**：界面上看着开训了、实际没人跑，比没有这个口更坏。
2. **报告生成** —— v5 的深度报告是 LLM 出的，而"LLM 出网"未定。
   存储与下载已就位（`ListReports` + HTTP），缺的只是"谁来生成"。

### 9.3 域私有状态的落点：**定了，是资产**

AICloud `C-10 §6` / `C-11 §5` 给的判据：

> 凡是界面上要能"看见它是什么时候采的、能不能重采"的，它就得是资产，不是中间量。

低频振动的基线（μ/σ、EWMA 起点）**两样都要** —— 换工况就得重采，运维必须看得见是哪段数据采的。
⇒ 落 `artifacts` 表、`kind='baseline'`，与标注/训练集/模型工件同级。
**不为它单开一套存储，也不让模块自己写文件。**（`artifacts.kind` 同时容得下 `C-11 §4` 的"图片工件"。）
