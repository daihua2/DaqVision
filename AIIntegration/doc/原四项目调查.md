# 原四项目调查 —— 订正与清单

调查缘起：AICloud `C-40 §5.4` 请我方评估 v5 的标量特征分类能否作为低频振动第③层。
查的过程中发现**本文与预研文档对 v4/v5 的刻画是错的**，且错法会影响选型与移植决策，故单立一节订正。

全部为 AISERVER **只读**核查（未改、未停服、未读原项目 `.env`，硬规矩 1）。

## 1 ★"v4 高频振动 / v5 低频振动"这个划分不成立

**两者的高频能力是同一份代码。** v5 的 `order_diagnosis/` 与 v4 的**逐位相同**（见 §18.2）。
真正的区别不是频段：

| | v4 | v5 |
| --- | --- | --- |
| `order_diagnosis`（阶次诊断：FFT / 包络 / 1X~5X 倍频 / 规则卡 / KNN 案例 / LLM） | ✅ | ✅ **同一份** |
| `press_diagnosis`（压装） | ✅ | ❌ |
| `servo_diagnosis`（伺服） | ✅ | ❌ |
| `robot_arm`（机械臂，走 InfluxDB） | ✅ | ❌ |
| 接实时库（`hs_realtime.py` 48KB）+ 工作台（标注/知识库/训练/归档/PDF） | ❌ | ✅ |
| 13 标量分类（`single_frame_models.py`） | ❌ | ✅ |

⇒ 准确的说法是：**v4 是「离线波形分析 + 四个机型的专用诊断」，v5 是「同一套阶次诊断 + 接入实时库的工作台闭环」。**

## 2 ★"两边 order_diagnosis 已经不一致"——今天不成立

逐文件 sha256：`constants / data_loader / evidence_builder / expert_knowledge / infer_baseline_model /
knn_case_retriever / llm_clients / llm_prompt_builder / rule_based_diagnoser / service / train_baseline_model`
共 12 个 `.py`，加 `rule_cards/` 下 5 个 YAML，**全部相同**。

原文那句可能当时成立、后来被同步（v5 在 2026-08-24 重建过，目录里还留着 `backend.codex-before-20260824-correct-project`），
也可能当初就记错了。★**不管哪种，本文此前的陈述与今天的现场不符，故订正。**
「同一套算法在新旧两处并存会漂」这个**风险判断仍然成立**，只是**它还没有发生**。

## 3 v5 有两条诊断路径 —— 路径一我方**早就知道并明确不移植**，错的是我方对它训练方法的判断

| | 路径一：**阶次诊断** | 路径二：**13 标量分类** |
| --- | --- | --- |
| 输入 | **波形 + 转速** → FFT → `amp_1x`~`amp_5x` 及占比 | 13 标量（温度 + 三轴×acc/freq/disp/vel） |
| 判据 | **规则卡**（5 个 YAML）+ 专家知识 + **KNN 案例检索** | sklearn 分类器 |
| 模型 | 手写 MLP（numpy），★**有 `_train_val_split(0.25)` 留出集** | RandomForest fallback，★**训练集自测** |
| 配套 | 证据包、LLM 基础/深度诊断、PDF 报告 | 无 |

★**路径一才是 v5 的主力，而且方法学上比路径二好得多。** 路径二是 v5 自己的**降级方案** ——
因为路径一要波形与转速，而现场（有人传感器）两样都没有，这正是 `AI-12` 定"v5 阶次诊断现场无输入、不移植"的原因。

⇒ **`C-40 §5.4` 请我方评估的那条，是 v5 的 B 方案，不是它的 A 方案。**

★**这里要分清我方到底错在哪，别把功劳和过失都记错**：

- **路径一的存在，我方早就知道**。`domains/vibration_lowfreq.py` 模块头 §0.1 白纸黑字写着：
  「原 v5 赖以立身的那套**阶次幅值 1X~5X + 规则卡 + MLP 工件**（`order_diagnosis/`）
  **在现场没有输入** —— 它喂的是 `services/acquisition.py::simulate_frame` 造的仿真波形。
  ⇒ 本域**不移植那套**。」**这个判断当时就做对了，且理由至今成立。**
- **我方真正错的是**：`AI-41 §4.2` 批评"v5 准确率是训练集自测、71 个模型全 1.0"时，
  **没有查路径一的训练代码**（`order_diagnosis/train_baseline_model.py` 是手写 MLP，
  **带 `_train_val_split(0.25)` 留出集**），于是把一个只对路径二成立的判断，说成了对 v5 整体的判断。
  ⇒ **范围说宽了，要向 AICloud 订正**（`AI-42` 待发）。

**教训**：批评第三方代码之前，要先确认自己看的是不是它的全部 —— 这与 AICloud 在 `C-39 §1.1`
自己认过的那条同形（"判据取在半路上"：读了存储层就下结论，没往上追调用方）。**两边先后犯了同一类错。**

## 4 v4 的"专用机型"是怎么回事

v4 不是一个振动项目，是**多机型诊断平台**（约 80 个路由）。除阶次振动外另有三类，**都不是振动**：

| 机型 | 输入 | 类别 |
| --- | --- | --- |
| **压装** `press_diagnosis` | `position_mm` / `velocity_mm_s` / `force_N` —— **力-位移曲线** | 正常压装 / 卡滞 / 压装不到位 / 配合间隙异常 |
| **伺服** `servo_diagnosis` | 9 个**伺服驱动内部量**（位置指令 / 实际位置 / 跟随误差 / 转速 / 转矩 / Iq / 电机·轴承·IGBT 温度），10 Hz、20 秒窗 | 正常 / 轴承退化 |
| **机械臂** `robot_arm` | 走 InfluxDB，独立报告生成 | —— |

另有三项**与机型无关的能力**，此前我方完全没记过：

- **零样本诊断** `/api/diagnosis/zero-shot`：把 **FFT 图**喂多模态 LLM，不训练直接问；
- **模板预警** `/api/diagnosis/template-warning`：拿一段历史帧当模板（**至少 5 帧**）与当前帧比对
  —— ★**与我方第②层"对着这台机器自己的基线比"是同一个思路**，值得对照；
- **多机型报告**：`generate_report` / `generate_servo_report` / `generate_robot_arm_report` / `generate_press_report`。

## 5 对我方的四条后果

1. **阶次诊断只有一份，不是两份。** 将来若上能到 L2/L3b 的传感器（维特 VB02 / 仁科 RS-WZ3P），
   要移植的就是这一份，不必在 v4/v5 之间选。
2. ★**`rule_cards/*.yaml` 是资产**：五张规则卡是专家知识的结构化沉淀（什么倍频组合指向什么故障）。
   现场暂时没有倍频输入用不上，但**换传感器之后直接可用，且比训一个分类器可靠**。
3. **我方"四个域"的划分照的是错的图景。** `vibration_lowfreq` 这个域名没问题（它确实做低频标量），
   但"将来做一个 `vibration_highfreq` 域对应 v4"这个假设**站不住** —— v4 里真正独有的是压装/伺服/机械臂，
   那是三个**别的机型**，不是高频振动。
4. **压装与伺服这两类的输入我方现在一路都没有**（力、位移、伺服遥测）。
   要接它们不是"加一个域"，是先要有那些点。**这一条在讨论"原项目停止演进"时是硬依据。**

## 6 ★算法模块清单（去重后 **11 个**，2026-09-16 只读核查）

此前本文与预研文档按"四个项目 = 四类能力"记账。**那个粒度太粗**：四个项目里实际有 11 个
互不重复的算法模块，而我方域的划分是按模块走的（一个域 = 一个 `.py`），所以要按这个粒度记。

**去重规则**：同一份代码 / 同一个模型出现在两处只算一个 ——
① `order_diagnosis` 在 v4 与 v5 中 **sha256 逐位相同**（§18.2）；
② ★**机械臂复用伺服的模型**（`robot_arm_fault_segments` 调 `_servo_predict`，
   特征也是同样 9 个伺服量），**不算独立模块**。

原因是初版只看到它有独立的路由、数据源与报告生成，**没有往下追它调的是谁的模型**。

#### 三个"专用机型"的算法细节（2026-09-16 实测）

| | 压装 | 伺服轴承退化 | 机械臂 |
| --- | --- | --- | --- |
| 输入 | `position_mm` / `velocity_mm_s` / `force_N` | 9 个伺服驱动内部量 | ★**同伺服那 9 个量** |
| 采样 / 窗 | 50 Hz，10 秒窗，12 窗/CSV | 10 Hz，20 秒窗，stride 5 秒 | 窗 200 / stride 50 |
| 模型 | **SVM**（吃 11 个统计量×3 路）+ **CNN-LSTM**（torch）+ scaler | **CNN-LSTM** + **决策树** + **SVM**（后两者共用 scaler） | ★**无自有模型，调 `_servo_predict`** |
| 类别 | 4 类：正常压装 / 卡滞 / 压装不到位 / 配合间隙异常 | 2 类：正常 / 轴承退化 | 同伺服 |
| 训练方法 | 60 epochs、lr 1e-3、weight_decay 1e-4、**patience 12 早停**、`random_state 42`、★**有 `split_press.json` 划分文件** | —— | —— |
| 数据来源 | ★`数据产生/压力机/压装故障批量数据集_2026-07-24` —— **合成** | 未查到训练代码与数据 | 同伺服 |

`servo` 的 CNN-LSTM 架构：`Conv1d(9→32,k=5)+BN+ReLU+MaxPool` → `Conv1d(32→64,k=5)+BN+ReLU+MaxPool`
→ `LSTM` → `Dropout(0.2)` → `Linear`。

**伺服那条再补四条**（2026-09-17 实测）：

- ★**它不是振动诊断** —— 一个振动传感器都不用，全靠**伺服驱动器内部遥测**。
  要接它需要的是**驱动器通讯口**（读内部寄存器），与振动那条采集路径完全不同。
- **两条推理路并存**，运行时按 `model` 参数选：树模型路（99 维统计特征 + scaler → 决策树 / SVM）
  与深度路（原始 `(200×9)` 时序 → CNN-LSTM）。
- ★**99 维里约 18 维是重复的**：`_window_features()` 每列吐 11 个统计量，其中 `ptp` 被算了**两次**
  （第 7 位与第 11 位），且 `var` 与 `std` 数学等价。树模型会忽略，但说明这块没仔细过。
- **源码注释自陈**：「其余故障类型保留在 `FAULT_MODES` 里，方便以后扩展，**但默认链路只用前两个**」
  ⇒ 本来设计了更多类，**实际只做了 2 类**（正常 / 轴承退化）。
- ★**`Bearing_Temp` / `Motor_Temp` 当轴承退化的佐证 —— 与我方第②层的 `temp_rise` 是同一个思路**
  （振动没变而温度升了，多半是润滑/冷却）。**两个独立实现都走到这一条，说明它是这类问题的自然解。**

★**两条值得记的**：
1. **压装那条的训练方法是四个项目里最规范的**（早停 + 固定随机种子 + 独立划分文件）。
   与 v5 路径二（`fit` 后自测）形成对照 —— **同一批人写的代码，方法学差距可以很大，不能按项目一概而论。**
2. **压装与伺服的模型都不止一个**（SVM / 决策树 / CNN-LSTM 并存，运行时按 `model` 参数选）。
   ⇒ 若将来要移植，**"移植一个模块"实际是移植 2~3 个模型 + 一套选择逻辑**。

#### 三个对排期直接有用的数

1. **我方现在只落了 2 个**：`vibration_lowfreq`、`vision_helmet`（后者已落码、未上现场）。相对 11 个，**完成度不到 1/5**。
2. ★**现场真有输入的只有 5 个**：#2 / #7 / #8 / #9 / #10。
   其余六个要么缺波形（#1 / #3），要么缺那类设备的点（#5 / #6 / #11），要么卡在出网（#4）。
   ⇒ ★**眼下可做范围最多这 5 个，其中 4 个是视觉 —— 振动这条线上只剩 #2 一个，而它是最没把握的那个。**

   ★**订正**：本节初版把 #3 模板预警标成"现场有输入（任何时序）"，**错了**。
   它的特征提取 `_template_feature()` 第一行就是 `db.load_waveform()`，三个特征组
   （`spectrum` 谱 / `envelope` 包络 / `enhanced` 含峭度与 `amp_1x~3x` 倍频）**全要波形**。
   ⇒ 现场无输入。**这是同日第三次因"只看表层、没追到特征提取的第一行"而记错**
   （前两次：机械臂没追它调谁的模型、v5 训练方法没查另一条路径）。
   ★**此后凡在清单里标"现场有没有输入"，必须追到特征提取的第一行，看它读的是什么。**

   ★**但要分清实现与方法**：要波形的是 v4 的**特征选择**，不是**方法**。
   「最近邻距离 + 留一法定阈值」喂什么向量都成立，**包括我方现有的标量**，而且它
   **只需要正常样本、不需要故障标签** —— 这在现场是决定性优势（现场恰恰只有正常数据）。
   它与我方第②层是近亲：第②层是"和基线的 μ/σ 比"（隐含高斯假设），
   它是"和一组正常样本的最近邻距离比"（**不假设分布**）。
   ⇒ 但它**回答不了"是哪一类故障"**，所以**不是第③层的替代品**，是第②层的一般化。
3. **我方有一个原项目没有的能力**：`vibration_lowfreq` 的**第①层 ISO 10816-3 烈度判级** ——
   v5 没做过（它只有阶次规则与 13 标量分类）。这是我方按《算法侧改造方案》L1 档新做的。

#### 记这份清单的理由

「原项目退为参考实现、四个域一律整体重构」这条裁定（2026-09-10）是按**四个项目**下的。
**按模块看，工作量与可行性的分布完全不同** —— 振动这条线上现场能做的只有 2 个模块，
而视觉那条线有 4 个、输入齐全、模型现成。**排期该按这张表走，不该按"四个项目"走。**

## 7 ★原四项目的数据**没有一条是真实设备数据**（2026-09-16/17 逐个查实）

这一条单独记，因为它是讨论"原项目停止演进""要不要移植"时的硬依据，
也是我方这两天所有"训不出有意义的模型"的共同根因。

| 模块 | 数据来源 | 出处 |
| --- | --- | --- |
| 低频振动（现场 v1 那组点） | ★Node-RED「通路一」**区间内均匀随机数**（3.0~5.1 mm/s，每 100 ms）与 v5 仿真器**物理模型**（约 0.46 mm/s，每秒一条）**两路交错写入** | AICloud `C-38 §4` 实测 |
| 伺服 | `services/servo_simulator.py`（163 行）：`random.Random()` + 正弦叠噪声 + 偶发脉冲；★**`/api/servo/start` 的入参直接带 `fault`，你说造哪种它造哪种** | 本仓实测 |
| 压装 | `services/press_simulator.py`（161 行）；训练集是 `数据产生/压力机/压装故障批量数据集_2026-07-24` | 本仓实测 |
| 机械臂 | `robot_arm_store._run()`：`random.Random()` + `generate_row(...)` → 写 InfluxDB → 再读出来诊断 | 本仓实测 |
| VFD | `vfd_storage.py` 的 `_CodeWaveformGenerator`，源标记 `code://megavert_vfd_demo_v5` | 预研文档 §2.4 |
| v4 阶次振动 | `services/acquisition.py::simulate_frame` 造的仿真波形 | `domains/vibration_lowfreq.py` §0.1 早已记 |

⇒ **四个项目、六个数据面，全是造的，没有一个例外。** 模式完全一致：
**造数据 → 存库（InfluxDB / 实时库 / 本地 JSON）→ 读出来 → 判 → 出结论**，闭环跑在合成数据上。

#### 三条后果

1. ★**"模型能跑"与"模型有用"在这里是两回事。** 这些模型从没见过真实设备数据，
   它们学到的是**各自仿真器的形状**。移植一个从没见过真实数据的模型，**风险比不移植大** ——
   因为它会带着一个看起来很专业的准确率数字进入现场。
2. **我方 `data_origin`（契约 1.6）正是为这件事设计的**，但那一格的取值粒度还不够：
   「仿真」既盖不住"有物理模型的仿真"，也盖不住"纯随机数"，更盖不住"两者混写"。
   ⇒ 待 `C-40 §4.4` 数据源落定后再定更准的取值（`AI-41 §3` 已向 AICloud 说明）。
3. ★**这解释了为什么"先把算法搞定"这件事推不动**：不是算法难，是**四个项目里没有一条可信的输入**。
   任何模型工作的前置都是同一件事 —— 拿到真实数据。
