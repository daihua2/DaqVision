## 1 模块划分【已定】

**10 个模块 + 1 个跨模块解释层**，按 4 条判据切（优先级从高到低）：

| # | 判据 |
| --- | --- |
| 1a | 输入形态不同（`point` / `image` / 波形 / **事件批次**） |
| 1b | 输入角色集不相交 |
| 2 | 依赖不同（`domaindeps` 按模块判，缺依赖整个模块不铺） |
| 3 | 输出集不同 |

**不作为切分理由**：设备类型不同（靠 `binding` 区分）、概念归类（靠 `DomainInfo.category` 分组）。

⇒ ★**这个切法切的是「部署单元」**：一个 `.py` 能不能独立装、独立铺、独立出点。
**不是按信号性质分类** —— 实际上模块 1 vs 2 输入完全相同，7/8/9/10 输入全是 `image`，
它们是靠判据 2、3 切开的。

清单见 [模块划分.md §3](模块划分.md)。

## 2 框架由哪几个模块逼出来【实测】

**模块 1、2 对框架设计不提供新信息**（只是 `point` 的又一个实例）。
其余 8 个恰好覆盖全部 4 种输入形态：

| 模块 | 输入形态 | 考验框架的哪一面 |
| --- | --- | --- |
| 4 伺服、5 VFD | `point` | **不考验** —— 骨架已支持，落下去就能跑 |
| 7/8/9/10 视觉 | `image` | ★**依赖隔离**：输入全一样，但 torch / ultralytics / paddle 互相装不上 |
| 3 波形 | 波形 | **数据量级**：一帧几千点，取数方式与 `point` 不同 |
| **6 压装** | ★**事件/批次** | ★★**骨架完全没有这一格** —— 最大的缺口 |

⇒ **框架真正要动的只有三处**：① 事件/批次取数　② 依赖按模块隔离　③ 轻重分流与驻留。

## 3 原项目代码的复用方式【实测 2026-09-17】

**判据：推理入口是不是纯函数。**

| 方式 | 模块 | 依据 |
| --- | --- | --- |
| **甲 直接拿** | **4 伺服**（★仅深度路，见下）、**6 压装**、**5 VFD** | 入口分别是 `predict_rows(rows)` / `predict_rows(rows, model)` / `ModelBundle.predict(rows)`，模型工件齐全 |
| **乙 拿模型、推理层重写** | **7 安全帽**、**8/9/10 表计与 OCR** | 入口是 FastAPI 端点；指针表/数字表还靠 `subprocess` 调另一个子项目 |
| **丙 只能拿思路** | **3 波形** | 代码在，但现场无输入 |

★**乙类已有成功范例**：我方 [`vision_helmet.py`](../domains/vision_helmet.py) 拿原项目的
`yolo11n_safety_512_fp32.onnx`，推理层用 onnxruntime+numpy+cv2 重写（**不拖 torch/ultralytics**），
并有 `research/vision-onnx-parity/` 做过一致性验证。模块 5/8/9/10 可照此路子。

★**2026-09-17 已实测伺服那条，结论要订正**：

| 判据 | 结果 |
| --- | --- |
| 能 import，不拖 app/db/services | ✅ **深度路成立**（`servo_diagnosis.infer`） |
| 能加载工件、喂数据出结果 | ✅ 首次 **13.2 s**（含模型加载），之后 **46 ms/次** |
| ★**树模型路** | ❌ **失败**：`servo_diagnosis.tree_infer` → `ModuleNotFoundError: No module named 'services'` |

⇒ ★**「零业务耦合」只对深度路成立**。`tree_infer.py` 耦合了原项目的 `services` 包，要拆耦合才能用。
而 `原四项目调查 §6` 记过「两条推理路并存，运行时按 `model` 参数选」 ⇒
★**拿一个模块 ≠ 拿到它的全部能力**：伺服能直接拿的是 CNN-LSTM 那条，决策树 / SVM 那条要额外工作。

【未验证】**压装与 VFD 仍只读了代码、没跑过**。鉴于伺服已在树模型路上翻车，
★**不可由伺服的结果外推**，两个都要各自实测。

## 4 算法清单【实测】

除视觉外四个模块，算法归纳为**五个家族**：

| 家族 | 用在哪 |
| --- | --- |
| **时序深度** | CNN-LSTM（伺服、压装）、TCN（VFD） |
| **传统 ML** | SVM、决策树、随机森林 |
| **规则判据** | 规则卡 support/conflict 加权（波形） |
| **距离/最近邻** | KNN 案例检索、模板预警 |
| **手写 MLP** | 波形阶次诊断 |

**三条对框架有约束力的共性**：

1. ★**每个模块有 2~3 个模型并存**，运行时按 `model` 参数选
   ⇒ 框架要容得下「**同一模块多工件**」；
2. ★**除 VFD 外全是同一形态**：窗口 → 特征或深度 → 分类，输出"哪一类 + 概率"；
3. ★**VFD 跳出了分类**：`classifier(6类)` + `current_head(当前严重度)` + `future_head(30s/60s/120s 后严重度)`
   ⇒ 框架的输出集**不能假设"一个模块出一组同质结论"**，得容得下一个模块同时出**类别 + 分数 + 多个时间点的预测**。

## 5 训练形态【实测】

原项目里**只有一个模块做成了完整训练闭环**（v5 低频标量分类：界面标注 → `POST /api/lowfreq/train` → `fit` → 存工件）。
伺服 / 压装 / VFD **训练代码不在机器上**，只能推理，**不能重训**；而它们的模型全是合成数据训的。

⇒ **两种模块形态，框架都要支持，而我方骨架两个都已有**：

| 形态 | 含义 | 我方落点 |
| --- | --- | --- |
| **A 工件外部导入** | 模型在别处训好，导进来就用 | `admin.py import-artifact`（已有） |
| **B 在线训练** | 现场标注、现场训、现场出工件 | `train()` + `Dataset` + `TrainedArtifact`（已有） |

★**这一块我方已超出原项目**：我方有样本快照、`data_origin` 来源标记、工件版本、启用/停用、
训练任务进度；v5 那条链是 `fit` 完直接存盘（无留出集、无快照、无启停），
所以才会出现 71 个 `accuracy=1.0`。

★**重写训练代码有据可依**：原项目训练配置记录完整
（`config_press.yaml`：50Hz / 10s 窗 / batch 32 / 60 epochs / lr 1e-3 / patience 12 / random_state 42；
伺服 `meta.json`：9 个信号列名、2 类、10Hz、20s 窗、5s stride），**不用猜**。

★**还要容得下一件事**：**工件声明的类 ⊋ 实际启用的类**。
【实测】压装 `label_mapping_press.json` 是 6 类，而 `infer.py` 的 `ACTIVE_LABELS` 只有 4 类
（"漏装"、"零件破裂"被关掉）；伺服源码亦自陈"其余故障类型保留在 `FAULT_MODES` 里，默认链路只用前两个"。
⇒ **界面上必须说清哪些类是关掉的**，否则运维会以为模型能判"漏装"。

## 6 编排调度【已定部分】

详见 [推理编排与模型驻留.md](推理编排与模型驻留.md)。已定的是：

- **轻还是重：域自述，骨架不猜**（不按 `REQUIRES` 猜，那等于把"有无第三方依赖"当成"重不重"）；
- **模型驻留走内存预算制**，★**没有缺省值**（这台机器能给多少内存只有部署的人知道）；
- 常驻放不下时**按需加载**，且★**按需模式必须成批** ⇒ 队列语义是**按域成组**，不是严格 FIFO；
- **队列顶替 + 背压不静默**（照搬 `logstore` 纪律）；推理**不能照抄 trainer 的串行排队**——训练人触发可以等，推理有节拍等不了；
- `/health` 要说得出真话。

★**一条硬约束**：三个视觉框架同时常驻大概率放不下，而 **OOM 时 Linux killer 可能杀掉的是 `historystored`**
—— 所以驻留预算不是优化，是躲不掉的前置。

## 7 组态配置【已定部分】

- **绑定机制**：域 + `binding` + 角色→点映射 + 台账参数。**同一批点可建多条绑定、各绑不同模块**
  ⇒ ★「一个采集点上叠加多个算法」**靠绑定实现，不靠切模块**；
- `declare()` 是**静态自述**，前端按 `DomainInfo.inputs` / `param_specs` / `outputs` 渲染，**契约不动**；
- `ParamSpec.level`（`machine` / `position`）：AICloud `C-40 §3.2` 请求，我方 `AI-41 §2.1` **已接受**；
- 【待提契约】`DomainInfo.category`（界面按大类分组）、`Declaration.weight`（轻/重）。

## 8 数据流转【2026-09-17 订正：两类，不是一类】

★**本节初稿把图片、波形、压装曲线一并当作「大对象点」，这是错的**（用户当日指出，见 `AI-43`）。
波形与压装曲线**本来就是 VQT 时序**，只是采样率高：
打包成字节块会丢掉逐点时间戳与逐点质量码，让实时库无法按时段取其中一截，
格式还变成我方私有 —— 违背了「纳入实时库是为共用一整套语义」的初衷。

| 输入形态 | 本质 | 怎么进来 |
| --- | --- | --- |
| `point`（标量） | VQT 时序 | 骨架按节拍取窗 → frame → `infer` → 结论点回写 ✅ **在跑** |
| **波形** | ★**VQT 时序**（每轴一个点，25.6 kHz） | 同上，**同一套语义**，差别只在采样率与是否连续采 |
| **压装曲线** | ★**VQT 时序**（三个点 @50 Hz，一次动作一个时段） | 同上 + **时段边界**（见下） |
| **图片 / 视频** | ★**大对象**（`bytes`） | 唯一真正的大对象；`AI-42` 那几条只对它成立 |

### 8.1 ★结构化 VQT 的存储参数【已定】

【已定】用户 2026-09-17 裁定：**这类点一律 `compErr = 0`，先不做 SDT 处理**。

⇒ hs 不必为此新增实现，**我方建点时自行保证**。
理由：`compErr` 非 0 即启用旋转门(SDT)压缩，**波形一旦被抽稀就不再是波形**，
而 FFT 出来的谱整个错，**界面上却仍然"有曲线"**。

【待 hs 确认】两条语义（`AI-43 §2.2`）：`compErr=0` 是否即"每采必存"；
此时 `QualityPending(5004)`（会被订正的值）是否绝不出现。

### 8.2 ★★真正缺的一格：时段 / 事件边界

用「大对象」提法时这个问题被绕过去了，订正后必须正面回答：

- **一次压装是一个事件** —— 那条曲线属于那一次动作，不属于"最近 10 秒"；
  两次压装之间的空闲段不该被当成样本；
- **一帧波形是一个采集单元** —— 0.1 秒的 2560 点是一帧，跨帧拼接没有物理意义。

而实时库现在只能按**绝对时间**取。两条路【待 hs 定夺，`AI-43 §2.5`】：

| | 做法 | 代价 |
| --- | --- | --- |
| ★**(a) 边界标记点** | 另建一个点，事件开始/结束各写一个值 | 一个事件要读两个点；边界点与数据点的时序一致性谁保证 |
| (b) 我方自己记账 | 我方库里记「第 N 次压装 = t1~t2」 | 实时库里那段数据**没有事件语义**，别的消费方看不出来 |

我方倾向 (a)（事件语义留在实时库里，不只存在于我方账本），但这会新增一类点，**该由 hs 定**。

### 8.3 采样率这个元数据放在哪【待 hs 定夺】

没有采样率就算不了 FFT，**算出来的频率轴整个是错的，而界面上看不出异常**。
`StoredPoint` 现有的 `valueType`/`step`/`canCtrlDown`/`reg` 都是「原样回吐、hs 不解释」类且各有既定语义，不宜借用。
三条候选见 `AI-43 §2.6`；我方倾向由 daqgate 在 `Paras` 里带、hs 原样回吐，**不倾向由我方台账自填**。

### 8.4 ★★图片那一路撞上硬规矩 2，必须先定夺

`推理编排与模型驻留.md §7` 写着：
> 若图片进了 iRtdb，**worker 可自己去取**，骨架只传引用 —— 那是最干净的形态。

而 `CLAUDE.md` 硬规矩 2 写着：
> **只有骨架进程持身份、连 historystore**。worker / 域不持证书、不连 hs ——
> 多进程共用一个 guid 会互相踢流、互删快照。

★**这两条直接冲突**。★**订正后这个冲突只对「图片/视频」成立** ——
波形与压装曲线既然是普通 VQT 点，骨架取了直接算或转交即可，量级与标量同级，不构成搬运压力。

**三个选项**【待定夺】：

| 选项 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| **A 骨架搬字节** | 骨架从 hs 取到大对象，经 IPC 传给 worker | 守住硬规矩 2；但大对象过 IPC，**骨架内存与带宽都要背**，且 §6 那条 OOM 风险直接加剧 |
| **B worker 自己连 hs** | worker 持**独立只读身份**连 hs，骨架只传引用 | 最干净，但**要 hs 支持独立只读令牌**，且须确认"只读身份不踢流、不动快照"—— **硬规矩 2 的理由是否对只读成立，未经核实** |
| ★**C 骨架落盘、worker 读文件** | 骨架从 hs 取到大对象 → 写本地临时文件 → 只把**路径**传给 worker → worker 读完即删 | ★**守住硬规矩 2**（仍只有骨架连 hs），又**不在 IPC 里搬大字节**；代价是一次落盘 I/O 与临时文件的清理责任 |

⇒ 我方倾向 **C**，但这是【待定夺】—— 它决定 worker 的形态，改起来代价大，不该我方自定。
★若选 B，须先向 historystore 发函确认"只读身份"的语义，**不能假设**。
