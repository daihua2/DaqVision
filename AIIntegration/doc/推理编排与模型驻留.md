# 推理编排与模型驻留

> 2026-09-16 · 用户定调：**资源允许就常驻，否则按需加载**。
> 本文把这句话落成可实现、可验证的设计。**尚未落码** —— 落码前请先读 §7 的待决项。

## 0. 为什么需要这一层（不是优化，是躲不掉的前置）

分界文档 §2 第 6 条早就写着：**单进程多域共享算力，只能由宿主统一编排**。
但至今**只有训练那一半兑现了**（`trainer` 串行一条、其余排队），**推理这一半没有** ——
调度器是**每条绑定一个线程**（`scheduler.py` 的 `_threads` 按 `(域, 绑定)` 建），彼此并行、互不相让。

测点类域看不出问题（每拍几个统计量，毫秒级）。但视觉一上现场就会炸，因为：

| 域 | 依赖 | 单次推理 |
| --- | --- | --- |
| 低频振动 | 无（纯 stdlib） | 毫秒 |
| 安全帽 | onnxruntime | 百毫秒~秒 |
| 指针表 | **torch + torchvision** | 秒 |
| 数字表 | **ultralytics**（拖 torch） | 秒 |
| 通用 OCR | **paddlepaddle + paddleocr** | 秒 |

⇒ **三个深度学习框架同时推理**，CPU 与内存都会抢，而推理是**有节拍的** —— 抢输了就掉拍。

### 0.1 现场的硬约束

AISERVER：总内存 **8 GB**，2026-09-16 实测**可用约 3.1 GB**
（daqgate 在 2026-09-10 还主动知会过"整机内存吃紧、只剩 433 MiB 空闲，`historystored` 有 584 MiB 被换出"）。

★**三个框架同时常驻大概率放不下。** 这不是性能问题 —— **OOM 时 Linux 的 killer 可能杀掉的是 `historystored`**，
那会让整个平台的数据面断掉。⇒ **内存必须是显式管理的预算，不能靠"试试看"。**

## 1. 总体形态

```
          ┌─ 轻量域（振动…）──→ 调度线程里直接算（现状不变，零风险）
调度器 ───┤
          └─ 重型域（视觉…）──→ 推理队列 ──→ worker（1~N 个）──→ 模型驻留管理
```

**三条边界，每条都有理由：**

1. **轻重分流**：把毫秒级的东西和几十秒的东西排进同一个队列，是让快的等慢的。
2. **worker 是独立进程**：内存隔离、崩溃隔离（paddle 段错误不该掀翻振动），
   且★**不违反硬规矩 2** —— worker 只算不连 hs，证书仍只在骨架手里。
   **这正是那条规矩当初预留的形态**（README §6：worker 不持证书、不连 hs）。
3. **驻留由骨架统一管**，域不自己 load/unload —— 否则每个域各管各的，预算就没人守。

---

## 2. 轻还是重：**域自述，骨架不猜**

```
# Declaration 新增
weight: str = "light"       # light | heavy
```

- `light`（缺省）：在调度线程里直接算。**老域零改动。**
- `heavy`：进推理队列。

★**为什么不让骨架按 `REQUIRES` 猜**：那等于把"有没有第三方依赖"当成"重不重"。
一个域可能只依赖 `numpy` 却很轻，也可能纯 stdlib 却跑一个几十秒的迭代算法。
**猜错的样子是静默的**：要么轻的被塞进队列白等，要么重的在调度线程里把节拍拖垮。

## 3. 模型驻留：**预算制，不是"试试看"**

### 3.1 判据

```
AII_INFER_MEM_BUDGET_MB   推理进程的内存预算（必填，无缺省）
```

★**没有缺省值**，与 `PYV` 同一条道理：这台机器能给多少内存，只有部署的人知道；
骨架猜一个，猜大了就是 OOM 杀掉 `historystored`。

### 3.2 常驻还是按需

```
已常驻用量 + 本域预估用量 ≤ 预算   ⇒ 常驻
否则                              ⇒ 按需加载（用完卸载）
```

- **预估用量**从哪来：域自述一个初值（`Declaration.model_mem_mb`），
  ★**首次真正加载后实测 RSS 差值并覆盖它** —— 自述是给第一次用的，之后以实测为准。
- **实测值要落盘**，重启后仍有效（否则每次重启都按自述值重算一遍）。

### 3.3 常驻满了怎么办

**LRU 卸载**最久未用的那个，但★**正在推理的不卸**。

### 3.4 ★按需加载模式下必须成批

按需加载时，"来一个装一次"比串行推理还贵（`yolo11m` 权重 121 MB，加载数秒）。
⇒ 队列里若有多个**同域**请求，**一次加载连着跑完**再换下一个域。

★这条会改变队列的语义：**不是严格 FIFO，而是按域成组**。
代价是某个域的请求可能等得久一点 —— 所以 §4 的背压与 §5 的可观测必须到位。

## 4. 队列与背压：**丢可以，静默不可以**

### 4.1 顶替策略

队列满时，★**同一绑定的新请求顶替它自己那条未处理的旧请求**。

理由：同一个测点，**最新那帧才有意义**，旧的算出来也没人看。
这比"丢最老"或"拒绝入队"都更贴合有节拍的推理。

### 4.2 但不许静默

被顶替/丢弃的那一拍：

- **落一条降级结论**（质量码 `QualityBad`，`evidence` 写明"排队超限，本拍未算"）；
- **记一条日志**，不做"只记一次"的限流。

★这是仓里既有的纪律（`logstore` 模块头"背压不静默"、`fetch` 的"每个周期都报"）：
**不报错的空是最难查的一类** —— 界面上看不出区别，趋势曲线也不断，只是数不对。

## 5. 可观测：`/health` 要说得出真话

至少四格，且**只报事实**（`C-32` 那次的教训：`snapshot` 那格曾经在说假话）：

| 格 | 内容 |
| --- | --- |
| 队列 | 当前长度 / 上限 / 累计顶替数 |
| 驻留 | 哪几个域常驻、各占多少 MB、预算用了多少 |
| worker | 几个、各自在跑什么域、上次崩溃时刻 |
| 掉拍 | 各域累计"排队超限未算"的拍数 |

## 6. 这套东西不动什么

- **契约**：`Declaration.weight` / `model_mem_mb` 是**域自述**，前端按 `DomainInfo` 渲染；
  若要在界面上显示"这个域是重型"，`DomainInfo` 加两格即可，**纯加法**。
- **轻量域**：一行不改，仍在调度线程里算。
- **硬规矩 2**：worker 不持证书、不连 hs —— 本设计**强化**它，不是突破它。

## 7. ★待决项（落码前必须定）

| # | 待决 | 为什么现在不能定 |
| --- | --- | --- |
| 1 | worker 与骨架用什么通信（管道 / 本地 socket / 共享内存） | 取决于图片怎么传：若图片进了 iRtdb，worker 可自己去取，骨架只传引用；若仍是 push，就得传字节 |
| 2 | worker 崩溃后的重启退避策略 | 要先有一次真实的崩溃样本，否则退避参数是拍的 |
| 3 | 队列上限取多少 | 要有真实的推理耗时分布，现在没有 |
| 4 | 重型域是否需要"独占整机"档 | 等真有两个重型域同时上现场再说（不预写投机性代码） |

★**第 1 条是关键前置**：它与"图片/视频存不存 iRtdb"是同一个决定。
图片一旦成为采集点，worker 就能自己按引用取数，骨架只调度不搬字节 —— 那是最干净的形态。

## 8. 与既有设计的关系

| 既有 | 本文 |
| --- | --- |
| 分界 §2 第 6 条"单进程多域共享算力，只能由宿主统一编排" | ★本文是它**推理那一半**的兑现（训练那一半已由 `trainer` 兑现） |
| 硬规矩 2 "worker 不持证书、不连 hs" | 本文把预留的 worker 形态真正用起来 |
| `trainer` "串行一条，排队顺序 = 建任务顺序，不做优先级" | 推理**不能照抄**：训练是人触发的可以等，推理有节拍等不了 ⇒ 故有 §4 的顶替策略 |
| `logstore` "背压不静默" | §4.2 照搬 |
