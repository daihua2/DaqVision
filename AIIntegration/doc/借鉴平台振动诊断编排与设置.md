## 1 对象层级：设备 → 测点 → 采集策略（`C-42 §1` 少了一层）

【实测】测点树接口 `organization/itemAcqstrategyTreeV3`，样本设备「转子试验台-国振专用模型」：

```
设备（nodeType 5）
├ 电机端轴承水平振动（测点，nodeType 9，绑一个通道 channelId）
│   ├ 8k速度(2-1000)          ← 采集策略（nodeType 19）：同一通道按不同类型/频带各出一路
│   └ 32k加速度(0.1-20000)
├ 电机端轴承垂直振动（测点）
│   ├ 8k速度(2-1000)
│   └ 32k加速度(0.1-20000)
├ 电机端轴承水平温度（测点，槽类型 5，无下挂策略）
└ 电机端轴承垂直温度（测点）
```

- **测点 = 一个物理通道**（一个传感器一个方向）；**采集策略 = 该通道上的一种量**（速度/加速度 + 采样长度 + **分析频带**）。
  `C-42` 说"一个测点一种测量类型"，实际是一个测点下可挂多种。
- 总貌图把「电机端轴承水平」的振动两路 + 温度一路**并在一个位置卡片上显示**【实测】，但数据结构里位置不是实体，靠测点名拼【推断】。
- **频带写在策略名里**（`速度(2-1000)`、`加速度(0.1-20000)`）——速度有效值是在哪个频带上算的，平台是显式交代的。

## 2 振动诊断在一台设备上是怎么编排的

设备页（谱图多维呈现 → 选设备）的页签就是它的编排【实测】：

| 页签 | 做什么 | 配置在哪 |
| --- | --- | --- |
| 总貌图 / 实时数据 / 历史数据 | 各测点各策略的当前值、趋势 | 采集策略 |
| **机理诊断** | 诊断次数、上次故障、故障结论；右侧「模型特征频率」；按时间段「一键诊断」 | 设备引用的**机理诊断模型**（共享，`C-42 §5`） |
| **AI 诊断** | 故障分类 | **每台设备一份**：选 1 个算法 + 参数 + 多个测量类型及**权重**；显示「未训练 / 最后训练时间」 |
| 机理诊断模型 | 查看所引用模型 | —— |
| **AI 诊断样本** | 该设备的训练样本（添加 / 导入） | 样本按设备管理 |
| **健康度评价** | 结果是「**剩余可用时长（天）**」+ 参与的测点/策略/指标表 | **另一份模型**：回归算法（样本里为 SVR）+ 测量类型及权重（加速度 50%、位移 50%） |
| 健康度评价样本 / 体检中心 | 样本；体检汇总 | —— |

- 【实测】样本设备 AI 诊断：贝叶斯分类器，测量类型 加速度 10% / 速度 20% / 转速 30% / 温度 40%，状态「未训练」。
- 【实测】机理模型详情页的「数据源」= **引用该模型的设备列表**（本例 4 台，跨不同机构），可「添加绑定」。**模型 → 设备是一对多**。
- 【实测】诊断触发有两种：
  1. **手动**：设备页选时间段 +「一键诊断」。
  2. **自动**：全局参数 `auto_diagnosis_online`（新在线）/ `auto_diagnosis_socket`（老在线），不是按设备配，是**全租户每天一次定时**：
     `{"enable":true,"diagnosisTime":"17:01:00","diagnosisType":3,"dataType":0,"message":true,"audibleAlarm":false,"users":[…],
     "pushTemplate":"$Organization_Name& 的 $T_Device_Name& 经过诊断发现【$Position&】存在【$Fault&】，请及时处理。"}`
     —— 定时跑、结论按模板推消息给指定人员，结果进「设备自诊断报告」。`diagnosisType`、`dataType` 各值含义未见说明。
- 【实测】诊断前的数据门槛 `diag_min_result=1`：单条采样值小于门槛不下发；设备参与诊断的数据全低于门槛则不诊断，提示「未发现有效采样数值，请核实设备或传感器状态」——即**停机/传感器掉线时不出诊断结论**。
- 【实测】`measur_points_diagnos=true`：测点波形图上也有「诊断结果」按钮（测点级诊断，未展开）。
- 【实测：前端代码】**轴系要逐个绑定数据源（测点）**。前端提示原文：「根据设备结构，为诊断模型添加轴系，支持添加多个」「为轴系绑定组件信息，可更为精准的定位故障部位」「**为每个轴系分别绑定数据源，绑定后才能进行故障诊断**」「一个设备最多添加20个轴系」「该轴系已被绑定」；
  接口 `diagnosis/shaft/list/item_guids`（按测点查轴系）、`shaft_component/bingding`（轴系绑组件）。
  ★订正本文上一版的推断（「诊断时按设备下全部振动测点算」）——那是错的。
- 【实测】取特征频率时前端只传「轴系 + 转速」（`[{"rpm":750,"shaftName":"齿轮箱","shaftUniqueId":…}]`，750 = 模型转速 1500 × 转速系数 0.5），不带测点。

## 3 报警（诊断之前的一道）

| 设置 | 粒度 | 看到的字段 |
| --- | --- | --- |
| 报警策略模板（报警库） | 分类树（如「离心泵标准」「空压机类设备监测标准」）→ **每行一个「测点类型 × 采集策略」** | 报警库名称（例：`泵自由端4H_8k速度波形(2-1000)`、`泵自由端4H_温度`）、编码、槽类型、已关联测点/策略数；阈值在「编辑」里（未点开） |
| 标准报警库 | 行业 × 设备类型 × 测点 × 采集策略 → **所属标准** | 表头：行业、设备类型、设备编码/名称、测点名称/编码、采集策略、所属标准、启用状态（本账号为空） |
| 多指标联合报警 | 设备 × 测点 × 策略名称 | 是否启用、备注 |
| 延迟报警设置 | 测点 × 采集策略；另有「全局设置」 | 开启延迟报警、延迟报警模式 |
| 指标分类管理 | 一级：时域 256 / 频域 512 / 包络 768 / 角度域 1024；二级带**参数**（如角度域「70-90度」：频率上限 5000、频率下限 2000 …） | 二级可「参数选择（已绑定/未绑定）」 |

- 「离心泵标准」这种分类说明它的"标准"是**按设备类型打包的阈值模板**，不是在代码里查国标表【推断】；`C-42 §9` 说没看到 ISO/国标判级——结构上它是留了「所属标准」一格让人填。
- 【实测】全局延迟报警 `global_delay_alarm_setting` 分**有线振动 / 无线振动 / 非振动**三组，各有两种模式：
  **比例模式**（`duration` 秒内超限比例达 `percent`%，如有线振动 100 s 内 50%）与**连续数量模式**（连续 `cCount` 次，默认 10）；可指定参与延迟的指标。本账号三组均未启用。
  ⇒ 这就是我方模块 1 定案 1.4 暂缓的「防抖」，平台做成了两种可选模式。
- 【实测：前端代码】**报警门限两种来源**：人工填，或**自动铺设**（系统按历史数据算）。自动铺设的表单：
  - **基准数据设置**：时间范围、统计方式（见到「平均值」）、**数据过滤下限/上限（百分比，两者之和 ≤100，即两头各剔掉一截）** ⇒ 算出**基准值**（不能为 0）；
  - **门限等级设置**：高侧 正常/预警/警告/危险 四个**门限系数**，低侧 低正常/低预警/低警告/低危险 四个系数，须严格递增；**门限值 = 基准值 × 系数**【推断，由「系数」「基准值」命名推出】；至少选一个等级；
  - 接口 `calcThresholdValue/calcMeasureTypeThresholdValue`（单个）、`batchCalcIndexTypeThresholdValue`（按指标批量）；
  - 「系统计算门限值需要时间，将在报警策略设置保存后计算并生效」；
  - 限制：「**信号类型为速度的有效值不支持设置自动铺设**」（全局 `ignore_speed_calc_limit` 控制速度类策略是否参与批量计算）。
- 【实测：前端代码】**自适应报警**：在自动铺设基础上**定期重算基准**（字段 `adaptiveUpdateFrequency`），「自适应报警设置后，将在次日生效」，有「自适应更新记录」和「自适应报警曲线」可查（接口 `onlineAlarmUpdRecord/page`、`/dataCurve`）。
  ⇒ 与我方模块 2 自训基线同类：平台是「截尾平均 × 系数 → 分级阈值，按周期滚动更新」；我方是「中位数 + 四分位距 → z 分」，不滚动更新。

## 4 运行状态门控与存储

- **设备启停参数管理**【实测表头】：是否启用、名称、**表达式**、参数、备注 —— 用表达式（多半基于转速/电流等测点）判开停机【推断】。
- **联动变量管理**：另一个菜单，未展开。
- **数据存储策略**【实测】：按报警状态分四档（正常 / 预警 / 警告 / 危险）各设**存储间隔(s)与百分比**；
  四个开关：设备停机状态异常数据不存储、停机正常数据不存储、未知状态异常数据不存储、未知状态正常数据不存储。
  ⇒ 设备状态（运行 / 停机 / 未知）是一等公民，存储与诊断都看它。
- **上传数据清洗策略**：按采集策略配置（本次未选中策略，内容未见）。
  全局缺省 `online_clean_data`【实测】：模式 `ShockDec` / `sigma3OutDec` / `ShockDecEnv`（冲击剔除、3σ 离群剔除、带包络的冲击剔除），
  参数 低频阈值频率 `fThreshold`=10 Hz、峭度阈值 `kurThreshold`、低频能量百分比阈值 `ratioThreshold`=50%。——**波形上传前先剔坏数据**。
- 【实测】`online_halt_device_normal_data=false`：「停机数据按正常数据处理」默认关，即停机数据**不当正常数据**参与统计/报警。

## 5 采集

- 数据采集设置：数采器列表（按主板 IP）→ 主板和槽 → 通道【实测】；可选项同 `C-42 §3`。
- 第三方数据走「第三方接入槽」（槽类型 15）【实测：报警模板行】—— 非本厂硬件的数据也挂成槽/通道。

## 6 对我方的对照（供讨论，**未定案**）

| 平台做法 | 我方现状 | 差别 |
| --- | --- | --- |
| 测点下挂多个采集策略，频带写明 | 采集点是实时库点，频带/口径靠参数 `vel_is_rms` 由人确认 | 我方无「频带」概念；GB/T 6075.3 的速度有效值按 10–1000 Hz 计（<600 r/min 为 2–1000 Hz，依 ISO 原文 §5 推断国标同），频带不对判级会偏 |
| 机理模型共享、设备引用、一对多 | 定案 3.2 已改为参照此做法 | 一致 |
| AI 诊断与健康度评价是**两份独立模型**，都按设备配、都带测量类型权重 | 模块 2 自训基线出异常分；故障分类（2.3）暂缓；无剩余寿命输出 | 平台把「分类」和「剩余时长」分开配 |
| 报警模板按设备类型打包阈值，挂到测点×策略；另有延迟、联合报警 | 模块 1 直接按国标表判级，防抖暂缓 | 平台阈值可人改、可按行业套模板；我方是标准内置 |
| 设备运行状态由启停表达式判，存储/诊断跳过停机数据 | 无运行状态门控 | ★停机时的振动会被我方照常判级/进基线 |
| 诊断：手动按时间段 + 全租户每日定时一次，结论按模板推消息 | 我方按节拍（默认 60 s）自动跑，结论写实时库点 | 平台诊断频度低（日级），报警才是实时的 |
| 波形先清洗（冲击/3σ）、低于门槛不诊断 | 骨架层坏质量码不出 OK 结论；无「数值太小即停机」门槛 | 平台用幅值门槛兜停机/掉线 |
| 延迟报警两种模式（时间窗比例 / 连续 N 次），按有线/无线/非振动分组 | 防抖暂缓（定案 1.4） | 若做，可直接照这两种模式 |
| 自动铺设门限：截尾后取平均作基准值 × 四级系数（高低两侧）；自适应报警按周期重算、次日生效；速度有效值不支持 | 模块 2 自训基线：中位数 + IQR → 异常分；基线手动重采 | 平台产物是分级阈值、会滚动更新；我方产物是连续异常分、不滚动 |
| 轴系逐个绑定测点，未绑不能诊断；一台设备 ≤20 轴系 | 模块 3 定案 3.2 只说轴系+部件模型由设备引用 | ★我方还缺「轴系 ↔ 采集点」这一层绑定 |
